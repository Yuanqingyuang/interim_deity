## 三、Web v3 存档数据结构审查（决策 D-6 的前置工作）

> 用户裁决：**先做数据结构审查**，再决定是否实现导入器（`M11-06`）。以下是本环境可完成的审查结果。

### 3.1 Web v3 结构（来源：`js/state.js` `saveHead()`/`encTile()`、`project-docs/10 §3`）

| 层 | 结构 | 备注 |
|---|---|---|
| 顶层 | `{ v:3, seed, era, speed, over, power, faith, totalFaith, pop, stars, starProg, starMilestones, dayTime, time, wonders, wonderList, boostGrow, boostBuild, boostRain, chunks, logs, savedAt }` | 25 个字段 |
| 区块 | `{ cx, cy, tiles: TileEncoded[10][10] }` | 线性数组，非 Map |
| 地块（双形态） | 紧凑：`number`（仅高度）；完整：`[h, water, tree, zone, prog, built, variant]`（7 元组，**位置敏感**） | 实测紧凑态仅占约 12.4% |
| 精度 | `r2()` 2 位小数（power/faith/pop/time/boost*）；`r3()` 3 位小数（starProg/dayTime/h/prog） | |
| 迁移 | v1/v2（旧 40×40 `tiles` 二维数组）→ v3（区块） | `deserializeState()` 内迁移，读取限 `≤1024` |

### 3.2 与 Unity 目标 DTO 的差异（审查结论）

| 差异 | 影响 | 处理建议 |
|---|---|---|
| `chunks` 为**数组**（`[{cx,cy,tiles}]`），Unity DTO 计划用 `List<ChunkSaveData>` | ✅ 天然兼容（数组 ↔ List） | 无需转换 |
| 地块**双形态**编码（数字/7 元组） | Unity 若用强类型 `TileData`，需实现双形态解码器 | 需写解码分支；**位置顺序必须固定** |
| 字段名不同（`pop`/`era` vs Unity 的 `economy.pop`/`world.era`） | 需字段映射层 | 映射表化，避免散落 |
| `starProg`（Web 死字段）、`live`（运行期死字段） | 不应进入 Unity 模型 | **丢弃** |
| `logs`（压缩编码 `[code,t,x,y]`） | Unity 计划拆为"事件日志 + 叙事档案" | 需决定是否迁移旧日志（建议：不迁移，归档用新系统） |
| `wonderList`（在建/已建奇迹列表） | 与 Unity `WonderService` 状态对应 | 需映射 |
| 无 `schemaVersion` / `terrainGeneratorVersion` | Unity 需要 | Web 用 `v:3` 兼作版本；Unity 需新增字段 |

### 3.3 审查结论（供 D-6 二次裁决）

| 结论 | 说明 |
|---|---|
| **技术上可行** | 结构清晰、字段可枚举、双形态可解码，写导入器**没有结构性障碍** |
| **成本估计** | 约 **3 人日**（`M11-06` 原估）：解码器 + 字段映射 + 旧档边界校验 + 测试 |
| **风险** | ① `terrainGeneratorVersion` 在 Web 存档中不存在 → 无法判断旧档地形是否与 Unity 生成一致 → **导入后地形可能与原档不同**（这是最大问题）；② `logs` 语义迁移成本 |
| **建议** | **暂不实现导入器**；若确需"老玩家带档"，建议**只迁移"文明进度"（era/pop/faith/wonders/milestones）而不迁移地块地形**，由 Unity 用同 seed 重新生成地形。此方案需用户确认是否接受"地形不完全一致" |

> ⚠️ 本结论**不改变 Web 存档格式**（任务书要求 Web Demo 可独立运行）。
