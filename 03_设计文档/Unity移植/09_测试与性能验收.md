# 测试与性能验收

## 1. 测试层次

- EditMode：纯公式、资源结算、时代门槛、地形采样、分区合法性、存档 DTO。
- PlayMode：输入与 UI、建筑完成、奇迹触发、暂停/倍速、场景加载与保存恢复。
- 长时运行：区块扩张、建筑增多、存档反复读写、暂停恢复与资源增长。
- 平台验收：目标 PC 配置，之后再测移动端；不要用编辑器帧率替代构建版本性能。

## 2. 与 Web Demo 对照

固定 seed 与初始状态，执行相同操作序列并对照：
- 地形高度与水域分类；
- 分区与建筑完工位置；
- 每个 tick 的人口、粮食、产能、信仰；
- 时代进阶可用性；
- 奇迹完成时机；
- 最终通关状态。

如果 Unity 与 Web 的随机算法不同，应比较可观察规则和分布，而不是要求随机布局逐格完全一致；若需要逐格一致，则必须移植同一 RNG 与生成算法。

## 3. 性能风险基线

公开项目总结记录过大城性能治理：建筑与村民合批后，某个 era IV 满城场景 Draw Call 曾从 6352 降至约 230；测试环境还包括 SwiftShader 软渲染，其 FPS 不代表目标硬件。Unity 中应重新测量，不能把 Web 的 Draw Call 数直接当成 Unity 性能指标。

建议记录：
- 主线程与渲染线程耗时；
- 每帧 GC Alloc；
- 活跃区块数、逻辑建筑数、渲染实例数；
- Mesh 重建次数；
- 保存耗时和存档大小；
- 帧率 1% low；
- 不同地图规模下的内存增长。

## 4. 验收门槛

具体数字需要按目标设备设定。至少保证：
- 无持续 GC 分配导致的周期性卡顿；
- 不因远离世界原点而出现明显精度问题；
- 区块增多时没有每帧全世界扫描；
- 暂停后模拟状态稳定；
- 存档失败不损坏旧档；
- 结算与评分可从存档恢复；
- 所有时代均可通过，不存在被错误里程碑永久锁死的情况。
