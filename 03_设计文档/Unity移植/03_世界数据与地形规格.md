# 世界数据与地形规格

## 1. 已知规则基线

- 单个区块：10×10 tile。
- 初始区块布局：4×4 区块。
- 世界按需生成区块；有建筑的区块补齐 8 邻域。
- 地形生成由 seed 驱动，使用域扭曲、大陆度、脊状山脉、丘陵和河谷等组合。
- 已有工具：抬升、下沉、平整、引水、绿化。
- Web 端使用点采样河流遮罩，不应误写成完整 D8 水文模拟。

## 2. 数据结构建议

```csharp
[Serializable]
public struct TileCoord {
    public int x;
    public int z;
}

[Serializable]
public sealed class TileData {
    public float height;
    public TileKind kind;
    public ZoneKind zone;
    public BuildingState buildingState;
    public int buildingId;
    public bool isWater;
    public bool isVegetated;
}

[Serializable]
public sealed class ChunkData {
    public Vector2Int coord;
    public TileData[] tiles; // 固定 100 格
    public int generationVersion;
}

[Serializable]
public sealed class WorldState {
    public int seed;
    public int currentEra;
    public Dictionary<Vector2Int, ChunkData> chunks;
}
```

Unity 的 `JsonUtility` 对 Dictionary 支持有限。实际存档时建议用 `List<ChunkSaveData>` 表示区块列表，或选择经过验证的 JSON 库；不要直接假定上述运行时数据结构可由 JsonUtility 无损序列化。

## 3. 坐标与确定性

- 明确 tile 坐标、chunk 坐标和 Unity 世界坐标的换算规则。
- 负坐标必须使用数学意义上的 floor division，不能简单向零截断。
- 生成器使用独立、可复现的随机数流；不要依赖 UnityEngine.Random 的全局状态，否则特效或 UI 消耗随机数可能改变地图。
- 同 seed 与同生成器版本应得到相同地形。若未来修改算法，保存 `terrainGeneratorVersion`，决定旧存档是兼容加载还是提示重开。

## 4. 地形工具规则

每个工具应拆为：
1. 目标范围采样；
2. 预览与合法性检查；
3. 提交地形修改；
4. 更新受影响区块的 mesh / collider / 导航数据；
5. 记录 `TerrainEdited` 事件供日志、评分和剧情系统使用。

工具操作不要在每帧对全世界做扫描。只重算受影响 tile 与邻接范围；需要全局统计的评分指标，在结算时或增量缓存中计算。

## 5. 分区与自动建造

把“区域已划定”和“建筑已建成”作为不同状态。公开数值文档说明，资源产出以已建成建筑为口径，住房容量按已建成格计算；移植时不能把刚涂画的区域立即当成完整产出建筑。

将规则集中到 `PlacementValidator`，并让手动划区与自动选址调用同一套约束。若设计决定手动模式允许放宽约束，必须显式作为规则参数，而不是两套无意间不一致的代码。

## 6. 渲染建议

- 不要每格一个 GameObject。
- 按 chunk 生成地形 Mesh；对建筑重复部件使用 GPU Instancing 或合批。
- 逻辑建筑数量与渲染代理数量分离。Demo 有 `MAX_BUILD_MESH` 等渲染抽样上限，移植时必须确认这些上限只是视觉抽样，不会影响经济模拟。
- 区块加载、卸载与 mesh 重建应有预算，避免一次性重建全图。
