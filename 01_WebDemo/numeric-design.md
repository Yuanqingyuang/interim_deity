# 实习神明 · 数值体系设计（公式规范）

> 本文档定义《实习神明》全部需要公式约束的数值：常量、时代参数、建筑上下限、资源产出、人口上限、产能与建造速度。
> 曲线采用**方案 B（前慢后快）**，时代取值为 **E = 1…5**。

> **实现口径（2026-09-15 复查）**：奇迹消耗为 **信仰**（`WONDERS.faithCost`），非产能公式；
> `faithCost` 现由 `FAITH_ERA_BASE[E] × FAITH_FILL_SEC` **推导**，不再手填（见 §4 ④）。
> 星星改为 **每时代 3 个里程碑**（见 `js/config.js` MILESTONES），不再随 faithRate 时间累积；
> 进阶条件 = 人口达标 +（E2 起）本时代奇迹 + 星星 ≥ starCost + 产能/秒 ≥ GATE(E)=0.5×刚需工业产能；
> 粮/产/信仰与住房均按 **已建成 built** 产出。§8 打分场已实现（`js/terrain.js` 的
> `scoreIndustrialCell` / `findAutoSite` / `placeIndustryBatch`，2026-09-30 核对）；
> 建筑代理比由渲染抽样上限承担（`MAX_BUILD_MESH`，P2-A 后树亦合批，见 docs/project-plan.md §2.2）；
> §8.5 批次方阵**已确认不实施**（2026-10 决策：以代码为准，死值 `LAYOUT.batch` 已从 `formulas.js` 删除，
> 工业 2 格配对由 `AUTO.industryPerTick` 承担）。

> **里程碑必须与本时代奇迹对齐（2026-09-15 修复硬锁）**：`MILESTONES[E]` 的奇迹里程碑引用
> `G.wonders[E]`（本时代奇迹），因为 `startWonderPlacement` 只允许建造 `WONDERS[G.era]`。
> 若里程碑指向上一时代的奇迹 → 该星星永久不可得；而 `starCost = 3` 恰等于每时代里程碑数（**零冗余**），
> 缺 1 星即时代链**硬锁死**。HUD 的里程碑文案、底部进阶条与 `eraReady()` 判定必须同代同口径。

> **信仰库存上限（2026-09-15 新增）**：`faithCapOf(E) = faithCostOf(E) × FAITH_CAP_MULT`（默认 2×）。
> tick 产出与读档都会把 `G.faith` 截断到该上限。信仰只有奇迹一个出口，无上限会跨时代无限囤积
> （旧版本实测城邦时代囤到 2300 万，而奇迹只需 1.5 万 → 奇迹瞬间建成、信仰经济失效）。

> 本文件与 `js/config.js` 配合使用；参数变更请以本表为准并同步回代码。

## 〇、已锁定的设计决策

| 项 | 决策 |
|---|---|
| 增长曲线 | 方案 B 前慢后快：200 → 2,000 → 8,000 → 2万 → **6万**（E5 原定 10 万，2026-10 下调，见 §二注） |
| 建筑种类 | 四类核心：房子 / 农田 / 工业区 / 教堂 |

| 上下限口径 | low = 人口刚需；high = 时代容量 × 1.25 |

**核心口径（重要）**：村民数量 `N` 为**绝对人口**。时代缩放**只通过 T(E) 出现一次**；建筑数量 ∝ 人口，因此单产系数**不再乘时代倍率**（避免二次放大，这是原始模板的主要缺陷）。

## 三、公式集

### ① 时代
```
M(E) = T(E) / T(1)
```

### ② 人口（三重约束 + 分阶段主导）

> ⚠️ **编号约定（易错点）**：下表用 **1-based 时代编号 E = 1…5**（人类可读）。
> 而 `js/formulas.js:121 popCap()` 内部用 **0-based 的 era 下标**，其分段条件写作
> `E <= 1 / E <= 3 / else` —— 两者**共用符号 E 但基数不同**，换算关系为
> `下标 = 编号 − 1`。即 编号 1–2 ↔ 下标 0–1、编号 3–4 ↔ 下标 2–3、编号 5 ↔ 下标 4。
> 阅读代码时务必先确认 E 是哪一套（本项目历史上多次因口径混淆产生缺陷）。

```
N_high(E) = T(E)
N_low(E)  = T(E-1)            // E=1 时为 20

N_cap(E) =                              // E 为 1-based 时代编号
    E = 1..2   :  房子数 × C_HOUSE                    // 住房主导
    E = 3..4   : ⌊ 农田数 × C_FARM / R_FOOD ⌋         // 粮食主导
    E = 5      : ⌊ 工业数 × K_IND / R_INDPOP ⌋        // 产能主导

// 对应代码（js/formulas.js:121，E 为 0-based 下标）：
//   if(E <= 1)      cap = houses * C_HOUSE
//   else if(E <= 3) cap = floor(farms * C_FARM / R_FOOD)
//   else            cap = floor(industries * K_IND / R_INDPOP)

人口增长：
    N ← min( N_cap , N × (1 + g(E)·dt) + 0.6·dt )
    约束：粮食/秒 ≥ N × R_FOOD

缺粮衰减（2026-09-30 F2 补充，`formulas.js growPop`）：
    supported = 粮食/秒 ÷ R_FOOD
    deficit   = (N×R_FOOD − 粮食/秒) ÷ (N×R_FOOD)         // 缺口比例 0–1
    N ← supported − supported × min(0.5, deficit) × dt   // 按缺口比例连续回落
    说明：旧实现「每 tick 减半」与帧率耦合，低帧下人口数秒内从 20 崩到 1；
    现改为随 dt 连续衰减，人口平滑回落到供养线，不再硬截断。

开局初始条件（2026-09-30 F2 补充，`terrain.js seedVillage`）：
    开局在原点附近生成 5 房 + 1 农田，均为已建成态（住房上限 20 = 开局人口，粮 50/s）；
    原点若为水面则回退到最近陆地。设计前提：E1–2 人口上限 = 住房×C_HOUSE，
    零住房开局即 cap=0 → 人口崩溃，故必须自带初始村落。
```

### ③ 建筑上下限（四类通用）
```
人均系数 r_b：房子 0.25 | 农田 0.20 | 工业 0.15 | 教堂 0.05

建筑_low(E)  = ⌈ T(E) × r_b ⌉            // 刚需：不卡关
建筑_high(E) = ⌈ T(E) × r_b × K ⌉        // 时代容量：防溢出（K = 1.25）
```

### ④ 资源产出
```
粮食/秒   = 农田数 × C_FARM
粮食消耗/秒 = N × R_FOOD
信仰/秒   = (教堂数 × K_CHURCH + N × K_FAITH_POP) × D(E)     // D(E) 见下方「信仰的时代阻尼」
产能/秒   = 工业数 × K_IND
```

#### 信仰的时代阻尼 D(E)（2026-09-15 修订）

原始公式两项都**线性于人口**，而人口每时代涨 10~1000 倍、奇迹消耗只涨约 10 倍，
结果是后期信仰「秒出」（E5 仅需 0.001s 就能攒满太空电梯），信仰经济失效。

改为按时代给出**基准产出**，人口与教堂只决定时代内的相对进度：

```
D(E)      = FAITH_ERA_BASE[E] ÷ (0.2 × T(E))     // 0.2 = 刚需教堂数下 原始产出 / 人口
D         = [0.375, 0.375, 0.9375, 3.75, 7.5]   // 2026-09-28 随 T 下调自动重导（代码由 BASE/(0.2×T) 推导）
信仰/秒    = FAITH_ERA_BASE[E]                   // 满规模（人口达标 + 刚需教堂）
奇迹消耗    = FAITH_ERA_BASE[E] × FAITH_FILL_SEC  // 由产出推导，不再手填
信仰库存上限 = 奇迹消耗 × FAITH_CAP_MULT（默认 2） // faithCapOf(E)，tick 与读档均截断
```

**关键不变量**：每个时代「满规模攒满本时代奇迹」耗时一致 = `FAITH_FILL_SEC`（100s）。
这条不变量已写成回归断言（`test/r11-p3.test.mjs`），改动参数时会立刻报警。

**不变量 2**：`FAITH_CAP_MULT ≥ 1`，保证满规模下「攒满上限」耗时 ≥ `FAITH_FILL_SEC`，
使「攒信仰 → 建奇迹」的节奏在每个时代都成立（上限过小会让信仰刚产满就被截断，同样破坏节奏）。

### ⑤ 建造速度（建造快慢 = 需求 × 产能）
```
单位产能需求：c_build(E) = C0 × e(E)，   e(E) = 1.5^(E-1)
造价权重（2026-09-30 定稿，NUM.BUILD_COST）：cost(zone) = 房 0.6 | 田 0.8 | 工 1.6 | 堂 2.0
产能需求/秒  = Σ_zone 待建数(zone) × c_build(E) × cost(zone)
奇迹占用/秒  = wonderDraw(E) = buildingLow(E,工业) × K_IND     // 仅在建奇迹施工期，见 ⑥b
建造速度：    V(E) = V0 × clamp( (产能/秒 − wonderDraw) ÷ 产能需求/秒 , floor , 2.0 )

零工业特例（2026-09-30 F2）：floor = 工业数 > 0 ? 0.2 : 0.5
    0.2 下限假设「已有工业」；零工业开局 V = 0.014/s（单栋约 71 游戏秒），
    首栋住房建成远慢于人口压力 → 无工业时抬到村民「自建」底速 0.5×V0（约 14 秒/栋）。
```

> cost 按刚需配比 r_b 加权均值恰为 1.0（0.25×0.6 + 0.20×0.8 + 0.15×1.6 + 0.05×2.0 = 0.65 = Σr_b），
> 故 §4.3 的整体 V 曲线不变，造价权重只重新分配四类建筑之间的经济压力（工业/教堂更贵，房/田更便宜）。

### ⑥ 产能（第四资源）三大出口
```
a) 建造 / 升级建筑：持续扣产能（由 ⑤ 的 V 驱动）
b) 世界奇迹：coinCost(E) = 建造时长(E) × 产能/秒（施工期持续占用，见下注）
c) 时代进阶门槛：产能/秒 ≥ GATE(E)
```

> **b) 实现口径（2026-09-30 定稿，`formulas.js/wonderDrawPerSec`）**：游戏没有产能库存，只有产能流量（工业数 × K_IND），
> 奇迹消耗实现为**施工期持续占用**——在建奇迹期间，从建造速度供给侧持续扣除
> `wonderDraw(E) = buildingLow(E, 工业) × K_IND`（= 30 / 300 / 1,200 / 3,000 / 15,000，见 ⑤）。
> 施工总消耗 = 建造时长 × 占用流量 = 恰为 §4.4 表值（540 / 7,200 / 3.6万 / 10.8万 / 67.5万），
> 与「一次性消耗 coinCost(E)」数学等价，且无需引入新的资源库存系统。

## 五、关键校验（设计约束）

### 🔴 约束 1：产能主导阶段必须可达标
```
R_INDPOP ≤ R_IND × K_IND = 0.15    // 工业 r_b 水位（T×0.15）下 popCap ≥ T 的充要条件
```
- 取 `R_INDPOP = 0.01`（现值）→ E5 功能刚需工业 = `T(5) × R_INDPOP / K_IND` = **600 格** → 人口上限 **60,000 = T(5) ✓**
- 旧值 `R_INDPOP = 0.12` + 旧 `T(5) = 50 亿` → 刚需工业 **41.7 万格**，远超单格放置吞吐 **✗ 不可达**（S-03 根因，2026-09-28 修订）

### 🟢 结论 2：low / high 的意义被验证
三重约束在 **low 配置下系数恰好 = 1.00**（供需刚好持平）；乘 `K = 1.25` 后才产生 25% 富余。
→ `low` 保证不卡关，`high` 提供缓冲，两者不可合并。

### 🟡 结论 3：后期产能需求增长曲线
建造速度随时代单调下滑（0.084 → 0.017），维持满速所需工业配比从 **0.125 升到 0.633**。
→ 后期玩家必须大幅加建 / 升级工业区，形成「产能追赶」的长线目标。

## 八、建筑自动生成位置推算（方案乙 · 打分场）

> **机制前提**：玩家**只划「居住区」**作为锚点；农田 / 工业 / 教堂由系统在满足约束的空位**自动落位**。
> 建筑占 1 格，不可落在水面或已占用格。
>
> **实现差异注（2026-09-30 核对，2026-10 定稿：以代码为准，见 docs/project-plan.md §2.2）**：打分场已实现于 `js/terrain.js`
> （`scoreIndustrialCell` / `findAutoSite` / `placeIndustryBatch`），本节理想模型按实际实现口径修订如下：
> ① S(c) 方形度用**邻域代理**（统计周边 8 邻域占用），非全局簇包围盒计算 —— §8.2/§8.3 公式保留为理想参照；
> ② P(c) 罚分实现为**硬否决**（违规格直接排除出候选），而非在打分中扣 10 分；
> ③ §8.5 的批次方阵落位**确认不实施**（死值 `LAYOUT.batch` 已删除，自动放置为单格逐一打分；
>    工业 2 格配对节奏由 `AUTO.industryPerTick = 2` 承担）。

### 8.1 输入 / 输出

```
输入：居住区格集合 R、各类型目标数量 n_t、已建建筑集合 B、地形（水面 / 高度）
输出：本批次建筑的坐标列表 [(x, y), ...]
```

### 8.2 基础量

**到居住区距离**（切比雪夫距离，0 = 在居住区内）
```
D_res(c) = max( |cx − nearest(R).x| , |cy − nearest(R).y| )
```

**间隔**
```
gap(c, c') = max(|cx−c'x|, |cy−c'y|) − 1      // ≥0 表示至少相邻
规则：gap(农田, 农田) ≥ 0 ；其余任意组合 gap ≥ 1
```

**方形度**（衡量加入 c 后簇有多"正方"）
```
S(c) = n' / (w'·h')  ×  (1 − |w'−h'| / max(w',h'))
     = 填充率        ×   方正度          // 完美实心正方形 = 1
其中 w',h' = 加入 c 后簇包围盒的宽 / 高，n' = 加入后格子数
```
> **实现口径**：上式为理想参照；实际实现（`terrain.js`）用**邻域代理**——统计 c 周边 8 邻域的占用数近似方形度，不做全局簇包围盒计算。

**区块（Chunk）** —— 渲染以 10×10 区块为单位
```
区块尺寸   S_chunk = 10
区块坐标   C(c) = ( ⌊cx / 10⌋ , ⌊cy / 10⌋ )
区块距离   D_chunk(C₁, C₂) = max( |ΔCx| , |ΔCy| )      // 以区块为单位
区块负载   occupancy(C) = 区块内建筑数 ÷ BlockCap      // 硬约束：occupancy < 1
区块容量   BlockCap = 25 座/区块
```
> 地图 34×34 → 区块 4×4 = **16 个区块**；同区块内最大切比雪夫距离 = **9 格**。

### 8.3 打分函数

```
score(c) = w₁·S(c) + w₂·A_same(c) + w₃·A_other(c) + w₄·A_anchor(c) + w₅·A_chunk(c) − P(c)

A_same(c)   = 1 / (1 + d_same)                  // 同类吸引：越近越高
A_other(c)  = min(1, d_other / D_max)           // 异类排斥：越远越高
A_anchor(c) = 按类型取值（见 8.4）
A_chunk(c)  = 2.0·typeShare(C(c), t) − 1.0·occupancy(C(c))    // 区块亲和
              typeShare = 区块内 t 类建筑数 ÷ 区块内建筑总数（空区块取 0.5 中性）
P(c) = 10·[间隔违规] + 10·[D_res 越界] + 10·[区块满载] + 4·( max(0, (d_other − D_max) / D_max) )²

权重：w₁ = 3.0（方正）  w₂ = 2.0（同类聚集）  w₃ = 1.5（异类分离）  w₄ = 2.5（锚点）  w₅ = 2.0（区块）
```
> **实现口径**：P(c) 不进入打分——间隔违规 / D_res 越界 / 区块满载的候选格在打分前即被**硬否决**剔除，效果等价于罚分无穷大。

### 8.4 类型约束表

| 类型 | 批次大小 | D_res 合法域 | A_anchor | 与同类间隔 | 与其他间隔 |
|---|---|---|---|---|---|
| 教堂 | 1 | `[0, 0]`（居住区内） | `−D_res` | ≥1 | ≥1 |
| 房子 | 按缺口 | `[0, 0]`（居住区内） | `−D_res` | ≥1 | ≥1 |
| 农田 | 按缺口 | `[1, R_farm]`（紧邻带） | `1 − |D_res − 1| / R_farm` | **0** | ≥1 |
| 工业 | 2 | `[R_ind, ∞)`（远离） | `min(1, (D_res − R_ind) / R_ind)` | ≥1 | ≥1 |

> `D_res` 越界即在 `P(c)` 中重罚（10 分），因此每个类型只会在自己的合法环带内落位；
> `A_other` 抬高异类距离、`P_far` 惩罚超过 `D_max` 的情况 → 同时满足「独立」与「不相隔太远」。
>
> **实现口径**：「批次大小」列仅决定**每 tick 放置数量**（工业 = `AUTO.industryPerTick = 2`，教堂单座，房子/农田按缺口），
> 不构成 §8.5 的方阵形状约束——每格独立打分落位。

### 8.5 批次生成流程（**已确认不实施，保留为理想方案存档**）

> **2026-10 决策（以代码为准）**：批次方阵落位不接线，死值 `LAYOUT.batch` 已从 `formulas.js` 删除。
> 实际实现为**单格逐一打分落位**（`findAutoSite` 每座独立选点；工业 `placeIndustryBatch(G, 2)` 每 tick 至多 2 格，
> 由 `AUTO.industryPerTick` 控制）。以下伪代码仅作历史设计参照，不代表现行行为。

```
按优先级（由内到外）：教堂 → 房子 → 农田 → 工业
区块归属与"溢出到下一区块"的判定见 8.8。

for t in 优先级顺序:
    n = 本类型待建数_t
    while n > 0:
        k = min(n, batch_t)                 // 教堂 1，工业 2，其余 ≤ 9
        s = ⌈√k⌉                            // 方阵边长 → 规则①（正方，不是 T 字）
        offsets = { (i mod s, ⌊i/s⌋) : i = 0..k−1 }
        若 k < s²：从 4 个角开始剔除，保证剩余仍是方阵
        best = argmax over 候选左上角 c₀ 的 Σ score(c₀ + offset_i)
        落位 best；n -= k
```

**批次方阵示例**
```
k = 1 → 1×1      k = 2 → 1×2      k = 4 → 2×2
k = 5 → 3×3 去 4 角      k = 9 → 3×3
```

### 8.8 区块填充规则（fill-first + 溢出 · 四类通用）

**规则**：优先把同一类型填满它所在的区块；但若该区块内剩余地块**给其他类型打分更高**，则该建筑**溢出到下一个区块**。

```
对类型 t 的下一座建筑：
  C* = 候选区块
       = t 的簇所在区块；若 t 尚无建筑，取距居住区最近的合法区块

  在 C* 的合法空格上分别求两类最优分：
      s_t     = max  score_t(c)                      // 放 t 的最高分
      s_other = max  max_{t' ≠ t} score_{t'}(c)      // 放其他类型的最高分

  if s_t ≥ s_other:
      → 落位 argmax score_t(c)      // 本区块被 t 认领，继续填同类
  else:
      → 本区块留给其他类型，t 溢出到下一区块
        下一区块按 D_chunk 升序取（相邻优先），且 D_chunk ≤ D_chunk_max = 1
```

**区块类型归属**：一个区块的"归属类型" = 该区块内数量最多的建筑类型；后续同类型建筑优先回填该区块。

**各类型的候选区块与溢出范围**（溢出后仍必须落在该类型自己的合法域内）

| 类型 | 候选区块 C* | 溢出范围 | 溢出/落位后仍须满足 |
|---|---|---|---|
| 教堂 | 含居住区的区块 | 其他含居住区的相邻区块 | `D_res = 0`、`occupancy < BlockCap`、间隔 ≥1 |
| 房子 | 含居住区的区块 | 其他含居住区的相邻区块 | `D_res = 0`、`occupancy < BlockCap`、间隔 ≥1 |
| 农田 | 紧邻带（`D_res` 1–3）所在区块 | 紧邻带内的相邻区块 | `1 ≤ D_res ≤ R_farm`、间隔：同类 **0** / 异类 ≥1 |
| 工业 | 满足 `D_res ≥ R_ind` 的区块 | 满足 `D_res ≥ 6` 的相邻区块 | `D_res ≥ R_ind`、`occupancy < BlockCap`、间隔 ≥1 |

> **教堂 / 房子的特殊情况**：它们的合法域是 `D_res = 0`，只能落在居住区格子上；因此其"溢出"不是离开居住区，而是**在居住区横跨多个区块时，从当前居住区区块换到相邻的另一个居住区区块**。

**四类统一流程**
```
for t in [教堂, 房子, 农田, 工业]:            // 由内到外
    while 本类型待建数 > 0:
        C* = t 的簇所在区块（若 t 尚无建筑 → 合法域内距居住区最近的区块）
        s_t     = max  score_t(c)                over 合法空格 c ∈ C*
        s_other = max  max_{t' ≠ t} score_{t'}(c)

        if s_t ≥ s_other:  落位本区块（argmax score_t）
        else:              t 让出本区块，溢出到 D_chunk ≤ 1 的相邻区块

        落位前硬校验：该类型 D_res 合法域 ∧ occupancy < BlockCap ∧ 间隔规则
```

**示例**
```
· 工业簇所在区块剩余地块对农田打分更高 → 工业让出，落到相邻区块
· 农田簇所在区块剩余地块对房子/教堂打分更高 → 农田溢出到相邻的紧邻带区块
· 房子：居住区横跨 A/B 两区块时，A 块填满后溢出到 B 块（仍满足 D_res = 0）
```

**容量提示（待处理）**：区块物理容量 ≈ 16 × 25 = **400 座可见建筑**，而逻辑建筑 r_b 水位在 E4 / E5 达数千～数万格（2026-09-28 随 T 修订下调，旧值百万～亿级）→ 建筑需要与村民一致的「代理比」，否则数值与可渲染规模对不上。

「8 邻域空置」规则（`terrain.js canPlaceZoneAt`）把非农田建筑密度压到 **≤ 25%**，
而岛屿可建造格实测仅 **4,979~5,881 / 种子**，故**建筑地块硬上限 ≈ 1,350 个**。
而 E4/E5 的刚需水位（`buildingLow`）达数千～数万格 → **物理不可达**，
表现为「玩家把岛铺满也永远达不到该时代的人口目标」。

这与 §7 村民渲染遇到的是同一个问题：**逻辑规模可以很大，但世界里的格子有限**。
村民的方案是「1 个渲染村民代表 q 个村民」（`RENDER_Q`），建筑采用**同构**方案。

### 9.2 机制

引入建筑代理比 $q_{b}(E)$：**1 个地块代表 $q_b$ 栋逻辑建筑**。

$q_b(E) = \text{BUILD\_Q}[E] = [1,\; 1,\; 3,\; 6,\; 20] \quad (E = 1 \dots 5)$

由此把「逻辑建筑数」与「地块数」两个口径显式分离：

$\text{地块数} = \left\lceil \frac{\text{逻辑建筑数}}{q_b(E)} \right\rceil$

| 口径 | 公式 | 用途 |
|---|---|---|
| **逻辑数** | `buildingLow(E,z) = ⌈T(E) × r_b(z)⌉` | 产出、人口上限、里程碑阈值、数值核算表 |
| **地块数** | `buildingLowTiles = ⌈buildingLow ÷ q_b⌉` | 放置目标（`autoBuild` 的 `need[]`）、地块硬上限 |

> ⚠️ **两个口径不可混用**。传错会让后期产出少算 $q_b$ 倍（E5 差 **20 倍**）。
> 故 `formulas.js` 的调用点注释必须标明所持口径，测试亦对此有专门断言。

### 9.3 取值校准过程

$q_b$ 的取值由 `test/r16-build-q.test.mjs` **反推校准**：约束是「各时代**关键路径**地块数 ≤ 预算 1,250」
（预算来自 §9.1 的硬上限 1,350，留 100 格余量）。

| E | 逻辑刚需（房/田/工/堂） | $q_b$ | 关键路径地块数 | 预算 |
|---|---|---|---|---|
| 1 | 50 / 40 / 30 / 10 | 1 | 69 | 1,250 ✓ |
| 2 | 500 / 400 / 300 / 100 | 1 | 698 | 1,250 ✓ |
| 3 | 2,000 / 1,600 / 1,200 / 400 | 3 | 921 | 1,250 ✓ |
| 4 | 5,000 / 4,000 / 3,000 / 1,000 | 6 | 1,185 | 1,250 ✓ |
| 5 | 15,000 / 12,000 / 9,000 / 3,000 | 20 | 1,060 | 1,250 ✓ |

> **E3 取 3 而非 2**：这是回归测试**实测抓出**的 —— 若 $q_b(3)=2$，关键路径达 **1,380 格 > 1,250**，超预算。

**反向断言**（该测试同时锁定）：若**不引入** $q_b$（即 $q_b \equiv 1$），
E4 关键路径需 **6,500 格**、E5 需 **19,500 格**，均远超硬上限 → 时代链物理不可达。

### 9.4 副产物：建筑方向的多体聚落

$q_b > 1$ 的时代若仍渲染「1 格 = 1 栋房」，玩家会看到 1 栋房却被告知代表 20 栋，观感不成立。
故 `render.js _houseCluster` 在 $q_b > 1$ 时为每格补 **2~3 个缩小副楼**，
使「1 格 = N 栋」在画面上可信。副楼复用主楼的几何/材质缓存，**不新增合批槽位**。

### 9.5 与 RENDER_Q 的对照

| | 村民渲染 `RENDER_Q` | 建筑 `BUILD_Q` |
|---|---|---|
| 代理对象 | 1 村民模型 ↔ $q$ 个逻辑村民 | 1 地块 ↔ $q_b$ 栋逻辑建筑 |
| 取值 | 6.7 / 25 / 53.33 / 80 / 250 | 1 / 1 / 3 / 6 / 20 |
| 受影响 | 仅视觉数量 | **放置目标 + 视觉**（故必须同步改放置口径） |
| 逻辑口径 | 不变（`T(E)`） | 不变（`buildingLow/High`） |
