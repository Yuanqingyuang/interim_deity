# 实习神明 项目规划书

## 一 背景与范围

本轮全平台实测发现的三处缺陷（F1 WebKit 地形法线、F2 人口与建造数值、F3 窄屏顶栏）已修复，随提交 `2e7ca28` 合并并推送到 `origin/main`。本规划书以该提交为基准，把代码与仓库三份文档（`numeric-design.md`、`docs/project-summary.md`、`README.md`）逐条对照，回答三个问题：哪些文档条目因本轮修复或既有实现而需要更新，文档中描述了哪些尚未落地的功能，以及在此基础上建议轻量增加哪些功能。

对照只覆盖数值、建造、渲染、奇迹、音频与移动端适配等已在文档中立项的范围，不引入文档之外的新玩法。所有结论均来自代码与文档原文，未经实测的推断以 `[假设—待确认]` 标注。

## 二 文档与代码对照结论

对照发现两类偏差。一类是文档滞后于代码，即功能已按修复或既有实现落地，但文档仍停留在旧描述，需要更新文档。另一类是代码偏离文档，即实现与文档公式存在结构性差异，需要先确认以哪一边为准，再决定改代码还是改文档。

## 四 建议轻增的功能

以下增量按补全闭环、视觉成长、体验、工程四类组织，只描述要做什么与为什么，不涉及具体实现方式。成本档位分为低（数值或接线改动，不触架构）与中（触及渲染或批量落位逻辑）。

### 4.1 补全数值闭环

奇迹产能消耗（低成本，✅ 已完成）。在奇迹完工时按 §4.4 公式扣除一次性产能，使产能三出口完整。奇迹的 boost 字段（boostGrow/boostBuild/boostRain）已在 `main.js` tick 接线，补一个产能扣减点即可闭合 §3⑥。实际落地口径：游戏无产能库存，改为施工期内持续占用 `coinCost(E) ÷ 建造时长` 的产能流量，总消耗恰为 coinCost(E)。

各建筑造价明细（低成本，✅ 已完成）。把 §6「待定」落地为分建筑造价表，区分房屋、农田、工业、教堂的产能单价，使建造产能消耗可分类核算，也为后续经济难度调节提供旋钮。实际落地：`NUM.BUILD_COST = {房 0.6, 田 0.8, 工 1.6, 教 2.0}`（加权均值 1.0，不改变总量纲），tick 需求与 autoBuild 门控同口径加权。

### 4.2 视觉成长

渲染公式重标定与 RENDER_P 清理（低成本，✅ 已完成）。按新 T 曲线重标定对数系数，或改用 §7.2 建议的线性方案 `N_render = clamp(N ÷ q(E), min(E), max(E))`，使 E3/E4/E5 渲染数贴合目标 150/250/400。同时删除或同步陈旧的 `RENDER_P` 常量。此项为纯数值改动，但需回归 `test/r11-p3.test.mjs` 信仰不变量断言，避免连带破坏。实际落地：采用线性方案 `RENDER_Q = [6.7, 25, 53.33, 80, 250]`，各时代目标人口下输出恰为 30/80/150/250/400；`RENDER_P` 已删除；全量回归通过。

建筑视觉代理比（中成本）。为建筑引入与村民同构的代理比，高时代以一座可见建筑代表 q 座逻辑建筑，避免 E4/E5 渲染规模爆炸。此项触及渲染管线，建议在村民代理验证稳定后再做。

批次方阵接线（中成本）。把 `LAYOUT.batch` 接入 `placeIndustryBatch` 与 `findAutoSite`，让房屋与农田按方阵成片落位，提升聚落秩序感。需同步确认 §8.3 方形度公式是否一并补实现。

### 4.3 体验

最小音频集（低成本，✅ 已完成）。为放置、奇迹完工、时代进阶三类关键事件补音效，用 Web Audio 振荡器合成即可，无需外部音频资产，规避 `project-summary.md` §10 的资产依赖。实际落地：`js/audio.js` 振荡器合成三事件音效，顶栏 🔊 静音开关 + localStorage 持久化，首次用户手势解锁 AudioContext 以符合自动播放策略。

### 4.4 工程

调试跳时代与高人口压测（低成本，✅ 已完成）。在 `?debug=1` 面板增加跳时代与刷资源便签，并在 `test/browser` 矩阵补 E4/E5 人口压测步骤记录帧率，为移动端红线与建筑代理比决策提供实测依据。实际落地：调试面板含刷资源 / 刷建筑 / 跳时代便签，`main.js` 另暴露 `__tdPan` / `__tdWonder` 压测探针（奇迹程序化落位，复用 placeWonder 校验）；`test/browser/stress-test.mjs` 16 阶段全绿（era I→IV 逐代刷建筑 + 奇迹 + 跳时代，末代 60×1s 城市视角长采样），压测结论见 §五。

## 五 优先级与排期建议

P0 先做文档校正与低成本数值闭环，因为它们风险低、收益直接，且能为后续改动建立准确基准。包括 §2.1 全部文档更新、奇迹产能消耗、各建筑造价明细、渲染公式重标定与 RENDER_P 清理。（✅ 已全部完成，随提交 `bf26226` 合并。）

P1 再做需实测支撑的工程项与体验项，包括调试跳时代与高人口压测、最小音频集。（✅ 已全部完成，压测 16 阶段全绿。）

### 5.1 P1 压测结论（2026-10，Playwright + Chromium SwiftShader 软渲染，1366×768）

规模爬坡数据（每代 dbgFill 刷满 + 奇迹建成 + 跳时代，城市视角采样）：

| 阶段 | 逻辑建筑（居/田/工/教） | 人口 | DrawCall | 三角面 | 平均 FPS |
|---|---|---|---|---|---|
| era I 刷建筑后 | 63/49/36/13 | 8 | 2152 | 6.1 万 | 0.8 |
| era II 刷建筑后 | 664/533/397/135 | 274 | 6361 | 17.7 万 | 1.8 |
| era III 刷建筑后 | 2587/529/921/135 | 13212 | 9632 | 39.1 万 | 1.8 |
| era IV 刷建筑后 | 2587/529/921/135 | 26450 | 6380 | 43.5 万 | 1.5 |
| era IV 长采样（60×1s） | 同上 | 26450 | 6364 | 43.5 万 | 1.2（峰值帧 2.2s） |

全程 pageErrors=0 / consoleErrors=0。FPS 为 SwiftShader 软渲染口径，真实 GPU 通常有 1–2 个数量级余量，绝对帧率不作红线依据；DrawCall 与三角面是 API 提交量，跨硬件可比，作为决策依据。

据此对 P2 两项做出决策：

1. **建筑代理比 q(E) 无需按原数值形态上马。** 渲染端已有 `MAX_BUILD_MESH = 420` 抽样上限（`render.js syncWorld` 对建筑网格按 `step = ceil(zoneCount/420)` 抽样），era IV 逻辑 4172 座建筑时可见建筑网格恒 ≤420 座——抽样上限已是事实上的建筑代理，§7.3 担心的「渲染规模爆炸」在建筑维度未发生（三角面 43.5 万中建筑占比受控）。
2. **DrawCall 治理必须上马，且对象是植被而非建筑。** DrawCall 峰值 9632 远超移动端红线（通常 <2000），主因是树木等植被网格无抽样上限、逐棵独立 draw；建筑抽样后 DrawCall 仍随植被规模爬升。P2 应优先做植被抽样上限或 InstancedMesh 合批，其次才是批次方阵（视觉秩序项，非性能项）。

P2 保留触及渲染管线的中成本项：植被 DrawCall 治理（新增，性能必做）、批次方阵接线（视觉选做）。原「建筑视觉代理比」降级为文档修订项——在 numeric-design §7.3/§8.6 注明渲染抽样上限已承担代理职责。§2.2 的基准确认结论仍是批次方阵的前置。

## 六 风险与假设

渲染公式重标定已完成并通过 `test/run-all.mjs` 全量回归，信仰节奏不变量断言未受影响；后续任何渲染数改动仍须全量回归。

批次方阵触及落位逻辑，属中成本改动，建议在 §2.2 基准确认后再实施。植被 DrawCall 治理（抽样上限或合批）触及渲染管线，压测已证实其必要性（峰值 9632），实施时以本压测脚本为前后对照基准。

§2.2 的三项代码偏离需先确认基准。本规划书 `[假设—待确认]` 建议以代码为准修订文档，因为现有打分场已能稳定落位，重写包围盒方形度与软扣惩罚的收益有限，但此假设需与数值设计意图核对后定稿。
