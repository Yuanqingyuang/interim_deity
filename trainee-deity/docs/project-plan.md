## 一 背景与范围

本轮全平台实测发现的三处缺陷（F1 WebKit 地形法线、F2 人口与建造数值、F3 窄屏顶栏）已修复，随提交 `2e7ca28` 合并并推送到 `origin/main`。本规划书以该提交为基准，把代码与仓库三份文档（`numeric-design.md`、`docs/project-summary.md`、`README.md`）逐条对照，回答三个问题：哪些文档条目因本轮修复或既有实现而需要更新，文档中描述了哪些尚未落地的功能，以及在此基础上建议轻量增加哪些功能。

对照只覆盖数值、建造、渲染、奇迹、音频与移动端适配等已在文档中立项的范围，不引入文档之外的新玩法。所有结论均来自代码与文档原文，未经实测的推断以 `[假设—待确认]` 标注。

## 二 文档与代码对照结论

据此对 P2 两项做出决策：

1. **建筑代理比 q(E) 无需按原数值形态上马。** 渲染端已有 `MAX_BUILD_MESH = 420` 抽样上限（`render.js syncWorld` 对建筑网格按 `step = ceil(zoneCount/420)` 抽样），era IV 逻辑 4172 座建筑时可见建筑网格恒 ≤420 座——抽样上限已是事实上的建筑代理，§7.3 担心的「渲染规模爆炸」在建筑维度未发生（三角面 43.5 万中建筑占比受控）。
2. **DrawCall 治理必须上马，且对象是植被而非建筑。** DrawCall 峰值 9632 远超移动端红线（通常 <2000），主因是树木等植被网格无抽样上限、逐棵独立 draw；建筑抽样后 DrawCall 仍随植被规模爬升。P2 应优先做植被抽样上限或 InstancedMesh 合批，其次才是批次方阵（视觉秩序项，非性能项）。⚠️ 此归因已被 P2 实测修正（见 §5.2）：满城场景树木早被建筑划拨清除，植被对 DrawCall 贡献 ≈0；真正大头是建筑/村民的多部件网格与阴影 pass。植被合批仍保留，定位为野外场景的防御性治理。

P2 保留触及渲染管线的中成本项：植被 DrawCall 治理（✅ P2-A 已完成，效果定位修正见 §5.2）、批次方阵接线（❎ 已定稿不实施，见 §4.2）。原「建筑视觉代理比」降级为文档修订项——在 numeric-design §7.3/§8.6 注明渲染抽样上限已承担代理职责。§2.2 的基准确认结论仍是批次方阵的前置。

**归因结论：P1「植被主导 DrawCall」的判断被证伪。** 建筑划拨会清除树木（`t.tree = 0`），满城世界（1089 区块）仅剩 2 个树格——满城场景里树本来就不存在，合批收益自然 ≈0（−28 draws 即残余树与野外边缘的微小贡献）。era III 的 +1102 是该轮城市规模更大（居 2691 vs 2587、采样时人口更高 → 村民/粒子更多）所致，非合批回退。

**P2-A 价值重定位**：保留为防御性治理——野外/边缘区块（未刷建筑）的树从逐棵 2–4 Mesh 恒定收敛为 ≤5 个 InstancedMesh draw，相机跨多少区块 DrawCall 上界不变；不再作为满城降 DrawCall 的主要手段。

**后续可选方向** → ✅ 已实施（2026-10 P3，见 §5.3）：建筑部件合并与村民部件合并两大头全部落地，era IV 满城 DrawCall 6352 → 230，移动端红线（<2000）达标；真机移动端帧率复测仍为后续观察项。

### 5.3 P3 建筑/村民部件合批：实施与压测对照（2026-10，同环境同口径）

针对 §5.2 归因出的两个真正大头（建筑 ~67% / 村民 ~27%）实施部件合批：

**P3-A 建筑槽位合批**（`render.js`）：以 12 个建筑模板（farm/house/church/factory × 3 外观代）用伪格跑一遍 `makeBuilding` 抽取部件清单，按 `(几何, 材质, castShadow, receiveShadow)` 聚合为 InstancedMesh 槽位，容量 = 单栋该槽位最大部件数 × `MAX_BUILD_MESH(420)`。仅完工建筑（`t.built`）入批，建造中建筑保留独立网格（进度缩放动画不受合批影响）；地块朝向用 `hash2(t._wx, t._wz, t.variant)` 确定性复算，双哈希签名跳过无变化重传；时代切换 `_clearBldInst()` 整批重建。vendor 无 BufferGeometryUtils，故不采用几何合并方案，统一走 InstancedMesh。
