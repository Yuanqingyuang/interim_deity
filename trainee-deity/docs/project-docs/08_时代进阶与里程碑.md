**时代倍率**

$$M(E) = \frac{T(E)}{T(1)} \tag{26}$$

$$T = [200,\ 2000,\ 8000,\ 20000,\ 60000] \qquad (\text{下标 } E = 1 \ldots 5)$$

**出处**：`numeric-design.md §一、§二` ｜ 实现 `js/formulas.js:11`

### 1.1 E5 目标从 10 万下调到 6 万（2026-10）

【已实现·规格已同步】出处：`numeric-design.md §二 2026-10 修订`

| 项 | 值 |
|---|---|
| 岛屿可建造格实测 | **4,979 ~ 5,881 / 种子** |
| 8 邻域空置后建筑地块硬上限 | **≈ 1,350 格** |
| E5 在 $q_b = 20$ 下的关键路径 | **≈ 1,210 格**（750 房 + 375 工 + 60 农田 + 里程碑） |
| 10 万目标所需 | 1,500 房格 + 750 工格 = **2,250 格** ✖ 超上限 |
| 6 万目标所需 | **1,210 格** ✔ 留出余量 |

**叙事跨度不受影响**：$200 \to 60{,}000$ 仍是 **300 倍**，逻辑口径仍是"星际时代 6 万子民"。

### 1.2 更早的一次修订（S-03，2026-09-28）

【出处】`numeric-design.md §二`

| 项 | 原值 | 改后 | 原因 |
|---|---|---|---|
| E3–E5 的 $T$ | 5万 / 500万 / 50亿 | 8千 / 2万 / （后改 6万） | 建筑放置为**单格**操作，AUTO 吞吐 ≈ 12 格/分钟；E4 需 **41.7 万格**工业、E5 需**十亿级**建筑 → **物理不可达** |
| `C_FARM` | 5 | **50** | 提高单建筑供养力，压低刚需格数 |
| `R_INDPOP` | 0.12 | **0.01** | 同上 |

**决策原则**：把 $T$ 下调到**放置吞吐可支撑**的区间，使各时代刚需建筑格数 ≤ 2,000 格。

## 二、进阶条件（四项）

【已实现】`js/progression.js:25 eraReadiness()`

$$\text{可进阶} \iff \underbrace{N \ge popGoal(E)}_{\text{①人口}} \wedge \underbrace{wonders[E]}_{\text{②奇迹}} \wedge \underbrace{stars \ge starCost(E)}_{\text{③星星}} \wedge \underbrace{\dot{I}_{out} \ge GATE(E)}_{\text{④产能}} \tag{27}$$

### 2.1 逐项说明

| # | 条件 | 判据 | 代码 | 备注 |
|---|---|---|---|---|
| ① | **人口** | $N \ge popGoal(E)$ | `G.pop >= popGoal` | E1 需 200；E5 已是终点不判 |
| ② | **本时代奇迹** | `!!G.wonders[era]` | `needWonder = era >= 1` | **E1 无需奇迹**；E2–E4 需要 |
| ③ | **星星** | $stars \ge 3$ | `starCost = 3` | 恒为 3（见 §三） |
| ④ | **产能** | $\dot{I}_{out} \ge GATE(E)$ | `gateOf(era)` | $= 0.5 \times$ 刚需工业产能 |

### 2.2 产能门槛

$$GATE(E) = 0.5 \times buildingLow(E, 3) \times K_{IND} \tag{9}$$

| E | 刚需工业（逻辑） | $GATE(E)$（产能/秒） |
|---|---|---|
| 1 | 30 | **15** |
| 2 | 300 | **150** |
| 3 | 1,200 | **600** |
| 4 | 3,000 | **1,500** |
| 5 | 9,000 | 4,500（已是终点） |

### 2.3 ⚠️ 四项条件必须**同口径**

【已实现】`progression.js:18-19` 注释明确警告：

> `gateOf` 是**逻辑口径**（$0.5 \times$ 逻辑刚需工业产能），
> 故地块数须**乘 `buildQ(era)` 后再比** —— 传错口径会让后期少算 `BUILD_Q` 倍（**E5 差 20 倍**）。

实现：

```js
const indTiles   = (G._builtCache && G._builtCache[3]) || 0;
const indLogical = indTiles * F.buildQ(era);      // ← 必须换算
const indPerSec  = F.industryPerSec(indLogical);
const gate       = F.gateOf(era);
```

**这行 `* F.buildQ(era)` 是硬锁事故的高发点**。历史上曾因此让某些种子永久停在工业 9/s、12/s。

### 2.4 返回结构（便于 UI 与排障）

【已实现】`eraReadiness()` 返回**不是布尔**，而是：

```js
{
  ok: boolean,              // 四项是否全满足
  reasons: string[],        // 未满足项的中文名（如 ['人口不足', '星星不足']）
  checks: {                 // 每项的实测值，供 UI 显示与排障
    era, pop, popGoal, stars, starCost,
    needWonder, wonderOk, indTiles, indLogical, indPerSec, gate
  }
}
```

**设计意图**：让 UI 能告诉玩家**具体缺什么**，而不是笼统的"条件未满足"；
也让排障时能直接读到每个量的实测值（无需重现）。

### 2.5 E5 是终点

【已实现】`progression.js:30`

```js
const isLastEra = era >= 4;
if(isLastEra) reasons.push('已是最终时代');
```

E5 不再进阶，通关条件是**建成太空电梯**（$G.wonders[4]$）。

## 三、里程碑与星星

### 3.1 零冗余设计【已实现】

$$starCost(E) = 3, \qquad \#MILESTONES[E] = 3 \quad \forall E$$

**即：每时代恰好 3 个里程碑，恰好需要 3 颗星 —— 零冗余。**

> ⚠️ **这意味着任一里程碑不可达 = 时代硬锁死。**
> 这是本项目**最贵的一次回归**，规格文档 `numeric-design.md:16-19` 专门记录：

> **里程碑必须与本时代奇迹对齐（2026-09-15 修复硬锁）**：
> `MILESTONES[E]` 的奇迹里程碑引用 `G.wonders[E]`（本时代奇迹），
> 因为 `startWonderPlacement` 只允许建造 `WONDERS[G.era]`。
> 若里程碑指向上一时代的奇迹 → 该星星永久不可得；
> 而 `starCost = 3` 恰等于每时代里程碑数（**零冗余**），缺 1 星即时代链**硬锁死**。
> HUD 的里程碑文案、底部进阶条与 `eraReady()` 判定必须**同代同口径**。

### 3.2 完整里程碑表

【已实现】`config.js:41 MILESTONES`

| E | #1 | #2 | #3（**必须是本时代奇迹**） |
|---|---|---|---|
| 1 | 人口≥50 | 农田≥10 | 教堂≥1 |
| 2 | 人口≥400 | 工业≥8 | **金字塔完成** ⟶ `G.wonders[1]` |
| 3 | 人口≥5000 | 农田≥80 | **大教堂完成** ⟶ `G.wonders[2]` |
| 4 | 人口≥1万 | 工业≥200 | **摩天塔完成** ⟶ `G.wonders[3]` |
| 5 | 人口≥5万 | 工业≥500 | **太空电梯完成** ⟶ `G.wonders[4]` |

**注意 E1 的 #3 是"教堂≥1"而非奇迹** —— 因为 E1 无需奇迹，故第 3 星用教堂代替。
这是刻意的，否则 E1 也会锁死。

### 3.3 里程碑判定口径

【已实现】`progression.js:62 claimMilestones()`

里程碑的 `check(G, ctx)` 签名中，`ctx` 提供四类建筑的**逻辑数**：

```js
export function claimMilestones(G, { farms = 0, inds = 0, churches = 0, houses = 0 } = {}){
  const qm = F.buildQ(era);
  const ctx = { farms: farms*qm, inds: inds*qm, churches: churches*qm, houses: houses*qm };
  //                         ↑ 入参是地块数，此处换算为逻辑数
}
```

**⚠️ 口径警告**【已实现】`progression.js:58-59` 注释：

> 入参 `farms/inds/churches/houses` 是**地块数**，内部乘 `buildQ(era)` 换算为逻辑数，
> 与 `MILESTONES[].check` 的阈值口径一致（config.js 注释如「农田≥10」「工业≥200」）。

**关键**：规格文档里的"农田≥10"等阈值是**逻辑口径**，
故 UI 显示时也必须换算，否则会出现"HUD 说未达标但实际已满足"。
为此 `milestoneSummary()` 与 `claimMilestones()` **共用同一换算**。

### 3.4 星星只由里程碑产生【已实现】

【出处】`config.js:39` 注释：

> **R5：星星仅由里程碑触发（每时代 3 个，一次性）。禁止纯 `faithRate` 时间出星。**

**即**：不能靠"信仰产出高"自动攒星。每个星都必须由**具体的一次性成就**获得。

**记账结构**：

```js
G.starMilestones = [[false,false,false], ...]   // 每时代 3 个布尔位
G.stars = number                                 // 当前可用星数（进阶时扣减）
```

`claimMilestones` 遍历该时代的 3 个里程碑，对**尚未置位**且 `check` 通过的项：
置位 → `G.stars += 1` → 记入 `newly[]` 返回（供调用方弹提示）。

## 四、进阶流程与状态迁移

### 4.1 完整流程

```
玩家点击「时代进阶」
   ↓
main.advanceEra()
   ├─ 清除地形拾取的旧格号缓存（避免进阶后拾取错位）
   ├─ eraReadiness(G)          ← 纯判定，不改 G
   ├─ 若 !ok → toast 具体缺项（用 reasons[]）
   ├─ applyEraAdvance(G)        ← 纯迁移，只改字段
   ├─ 刷新渲染 / HUD / 进阶条
   └─ sfxEra() + 粒子反馈
```

### 4.2 状态迁移（`applyEraAdvance`）

【已实现】`progression.js:107`

```js
export function applyEraAdvance(G){
  const from = G.era | 0;
  G.stars  = Math.max(0, G.stars - (ERAS[from]?.starCost ?? 0));   // 扣星
  G.era    = from + 1;                                             // 进阶
  G.starProg = 0;
  // 清残留输入态（见下）
  G.placingWonder = null;
  G.painting      = false;
  G.panning       = false;
  G.hover         = null;
  G.terrainDirty  = true;
  return { from, to: G.era, name: ERAS[G.era]?.name ?? '' };
}
```

**⚠️ 为何必须清"残留输入态"**【已实现·2026-10 审计发现】：

> 必须同时清掉「放置中」与「雕刻中」两类残留输入态 ——
> 否则进阶前若点过奇迹按钮或正卡着 `painting`，**新时代表格会继续被雕刻**，
> 且**奇迹按钮会永久停留在"放置中"样式**。

| 字段 | 若不清的后果 |
|---|---|
| `placingWonder` | 奇迹按钮永久停在"放置中"样式；点地图会误放奇迹 |
| `painting` | 新时代表格被继续雕刻（持续扣神力） |
| `panning` | 相机拖拽状态残留 |
| `hover` | 悬停高亮环停在上一个时代的位置 |

### 4.3 表现层与逻辑层分离【已实现】

【出处】`progression.js:9-10` 注释：

> 本模块**只做判定、不改 G**（除 `claimMilestones` 的位图与星数记账外无副作用），
> 所有表现（toast / 粒子 / 音效 / 渲染刷新）留在 `main.js`，便于测试与复用。

**这层分离的直接收益**：`progression.js` 是**纯逻辑、无 DOM 依赖**，
故可被 Node 直接单测 —— 而它承载的正是本项目最贵的那次回归。
回归测试 `test/rev-2-progression.test.mjs`（**78 条断言**）覆盖：

| 测试组 | 内容 |
|---|---|
| 逐条件隔离 | 四项条件各自独立验证（不满足时 `reasons` 精确指出） |
| 逻辑口径闸门 | 验证 `indTiles * buildQ(era)` 换算正确（防硬锁复发） |
| 星星位图 | 里程碑只加一次、不重复加星 |
| 进阶状态迁移 | 扣星、`era+1`、残留输入态被清除 |
| **五时代连续playthrough** | 从 E1 走到 E5 全程可达 |

## 五、时代进阶带来的全面变化

进阶不只是加数字，而是**六个维度的同步跃迁**：

| 维度 | E1 → E5 的变化 | 配置 |
|---|---|---|
| **数值目标** | 人口 200 → 60,000（300 倍） | `ERAS[].popGoal` |
| **建筑上下限** | `buildingLow/High` 按 $T(E)$ 缩放 | `formulas.js` |
| **建筑代理比** | $q_b$: 1 → 1 → 3 → 6 → 20 | `NUM.BUILD_Q` |
| **村民代理比** | $q$: 6.7 → 25 → 53.33 → 80 → 250 | `NUM.RENDER_Q` |
| **建筑形体** | 四类分区各换一套（共 **20 套**） | `BUILDING_STYLE` |
| **地形配色** | `PALETTES[era]` 换地表/水/天空/雾 | `PALETTES` |
| **信仰基准** | 15 → 150 → 1500 → 15000 → 150000（每代 ×10） | `FAITH_ERA_BASE` |
| **新奇迹** | 每代解锁一座 | `WONDERS[era]` |
| **机制转折** | E3 起人口上限由住房→粮食；E5 转产能 | `popCap()` |

**玩家感知最强的两项**：

1. **建筑形体全换** —— 整座城市"换了个时代的样子"（这是 2026-10 重构的重点，见 `06` 文档 §2）
2. **村民代理比跳变** —— E4→E5 时 $q$ 从 80 跳到 250，虽然渲染数只从 250 涨到 400，
   但玩家会看到"每个人代表更多子民"（通过 HUD 的绝对人口数字感知）

## 六、可达性求导（为何需要 `BUILD_Q`）

### 6.1 硬上限算术

$$N_{buildable} \approx 4{,}979 \sim 5{,}881 \ \text{格（岛屿可建）}$$

$$\text{密度上限} = 25\% \quad (\text{8 邻域空置规则})$$

$$\Rightarrow \quad N_{build,max} \approx 5{,}000 \times 0.25 = 1{,}250 \sim 1{,}350 \ \text{建筑地块}$$

### 6.2 关键路径地块数

**定义**：达成某时代进阶所需的**累计建筑地块数**（含历史时代已建的）。

$$C(E) = \underbrace{buildingLowTiles(E,1)}_{\text{住房}} + \underbrace{buildingLowTiles(E,2)}_{\text{农田}} + \underbrace{buildingLowTiles(E,3)}_{\text{工业}} + \underbrace{\text{里程碑需求}}_{\approx 25}$$

| E | $q_b$ | 住房 | 农田 | 工业 | 里程碑 | **合计** | 预算 1,250 |
|---|---|---|---|---|---|---|---|
| 1 | 1 | 50 | 40 | 30 | 25 | **69**† | ✔ |
| 2 | 1 | 500 | 400 | 300 | 25 | **698**† | ✔ |
| 3 | 3 | 667 | 534 | 400 | 25 | **921**† | ✔ |
| 4 | 6 | 834 | 667 | 500 | 25 | **1,185**† | ✔ |
| 5 | 20 | 750 | 600 | 450 | 25 | **1,060**† | ✔ |

† 表中数字为测试 `test/r16-build-q.test.mjs` 的**实测值**（与手算略有差异，因里程碑需求随时代不同）。

### 6.3 反向断言（不引入 `BUILD_Q` 会怎样）

$$q_b \equiv 1 \quad \Rightarrow \quad C(4) = 6{,}500, \quad C(5) = 19{,}500$$

**均远超硬上限 1,350** → **时代链物理不可达**。

### 6.4 E3 取 3 而非 2 —— 由回归测试实测抓出

【已实现·实测】`formulas.js:42-43` 注释：

> E3 取 3（非 2）：E3 人口 8000 → 2000 逻辑房，若只 ÷2 需 1000 房格，
> 加门槛工业与农田后达 **1380 格、超预算** —— 该超限由回归测试实测抓出。

**这体现了"预算约束驱动参数"的设计方法**：$q_b$ 不是估出来的，而是**反推校准**的。
