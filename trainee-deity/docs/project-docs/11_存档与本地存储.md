## 〇、总览：这是一个"零后端"的存档系统

| 项 | 实现 |
|---|---|
| 存储介质 | 浏览器 **`localStorage`** |
| 云端同步 | 【不适用】**无**。无后端、无账号服务器 |
| 账号模型 | 多用户，**纯本地**（`js/auth.js`） |
| 存档槽位 | 3 个手动槽 + 1 个快速档 |
| 手动迁移 | JSON 导出 / 导入 |
| 版本 | **v3**（含 v1、v2 迁移路径） |
| 序列化 | 双形态地块编码 + 分块异步 |

### 0.1 ⚠️ 需要向玩家明确的限制

| 限制 | 后果 |
|---|---|
| `localStorage` 是**单浏览器**存储 | 换设备 / 换浏览器 = 进度不共享 |
| 清理浏览器数据会**清除存档** | 进度永久丢失（除非曾导出 JSON） |
| 无云备份 | 无任何服务端副本 |
| 隐私模式 / 无痕窗口 | 关闭窗口即丢失 |

> 【待确认】`docs/deploy.md` 是否向玩家提示了这些限制。
> 从产品角度，**这是上线前应向玩家明确告知的第一件事**。

## 二、存档结构（v3）

### 2.1 顶层字段

【已实现】`js/state.js saveHead()`

```js
{
  v: 3,                                    // 存档版本
  seed, era, speed, over,                  // 世界与进度
  power, faith, totalFaith, pop,           // 资源与人口
  stars, starProg, starMilestones,         // 星与里程碑
  dayTime, time,                           // 时间
  wonders, wonderList,                     // 奇迹
  boostGrow, boostBuild, boostRain,        // 神迹剩余秒数
  chunks,                                  // 区块数组（主要体积）
  logs,                                    // 压缩编码日志
  savedAt,                                 // 写入时间戳
}
```

**完整字段字典见 `10_配置表与数据字典.md §3.1`。**

### 2.2 精度压缩

| 精度函数 | 含义 | 应用于 |
|---|---|---|
| `r2(x)` | 保留 2 位小数 | `power`、`faith`、`totalFaith`、`pop`、`time`、三个 `boost*` |
| `r3(x)` | 保留 3 位小数 | `starProg`、`dayTime`、地块 `h`、地块 `prog` |
| `int(x, def, lo, hi)` | 夹取整数 | `cx`、`cy`（读档时防御） |

**设计意图**：玩家看不出 `power = 123.456` 与 `123.46` 的区别，
但 2/3 位小数能显著压缩体积（存档是大图数 MB 级）。

### 2.3 地块双形态编码（体积关键）

【已实现】`js/state.js encTile()`

```js
function encTile(t){
  const h = r3(t.h);
  // 全部属性为默认值 → 只存一个数字
  if(!(t.water|0) && !(t.tree|0) && !(t.zone|0) && !(t.variant|0) && !t.built && !(+t.prog))
    return h;
  // 否则存 7 元组
  return [h, t.water|0, t.tree|0, t.zone|0, r3(t.prog), t.built?1:0, t.variant|0];
}
```

| 形态 | 类型 | 触发条件 | 体积 |
|---|---|---|---|
| **紧凑** | `number` | 未开发地块（`water/tree/zone/variant/built/prog` 全默认） | 1 个数字 |
| **完整** | `number[7]` | 有任意非默认属性 | 7 元组 |

**7 元组字段顺序（位置敏感）**

| 下标 | 字段 | 精度 |
|---|---|---|
| 0 | `h` | r3 |
| 1 | `water` | 0/1 |
| 2 | `tree` | 0/1 |
| 3 | `zone` | 0–4 |
| 4 | `prog` | r3 |
| 5 | `built` | 0/1 |
| 6 | `variant` | 0–2 |

> ⚠️ **`variant` 的默认值是 0**，但 `variant` 由哈希决定（可能为 1 或 2），
> 故约 2/3 的地块会因此走完整形态。
> **实测紧凑形态占比约 12.4%**（曾有一处注释写"绝大多数"，已更正）。

### 2.4 区块结构

```js
{ cx, cy, tiles: Array<Array<TileEncoded>> }   // 10 × 10
```

**区块几何由 `config.js CHUNK = 10` 决定**（`state.js` 与 `terrain.js` 共用同一来源）。

## 三、版本迁移

### 3.1 迁移路径

【已实现】`js/state.js deserializeState()`

```
读档入口
  ├─ data.v === 3 且 chunks 为数组  →  v3 路径（区块制）
  ├─ data.v === 2 或 1 且 tiles 为数组  →  旧 40×40 存档，迁移到区块
  └─ 其他  →  返回 false（读档失败）
```

### 3.2 v1 / v2 → v3 迁移

**旧结构**：`data.tiles` 为 2D 数组（旧版上限 40×40，代码中放宽到 1024）

**迁移算法**：

```js
for(let y = 0; y < oldRows; y++)
  for(let x = 0; x < oldCols; x++){
    const a = data.tiles[y][x];
    const {cx, cy} = worldToChunk(x, y);          // 世界坐标 → 区块坐标
    const k = chunkKey(cx, cy);
    if(!G.chunks.has(k)) G.chunks.set(k, {cx, cy, tiles: 空区块});
    decodeTileInto(G.chunks.get(k).tiles[y % CHUNK][x % CHUNK], a);
  }
```

**关键点**：
- 世界坐标到区块坐标用 `worldToChunk(x, y)`，块内偏移用 `% CHUNK`
- 迁移是**无损**的（每格都写入对应区块）
- 读取时限定 `oldRows/oldCols ≤ 1024` 防止畸形存档导致内存爆炸

### 3.3 地块解码兼容

【已实现】

```js
// 兼容两种编码：数字 = 只存高度的未开发地块；数组 = 完整 7 元组
const t = makeTile();
decodeTileInto(t, c.tiles[ly]?.[lx]);
```

`decodeTileInto` 同时接受 `number` 与 `number[7]` 两种形态。

### 3.4 读档的防御性校验（存档是不可信输入）

【已实现】`deserializeState()` 逐项校验：

| 校验 | 拒绝条件 |
|---|---|
| 顶层类型 | `!data \|\| typeof data !== 'object'` |
| 区块数组存在 | `!Array.isArray(data.chunks)` |
| 区块数量范围 | `length === 0` 或 `> MAX_SAVE_CHUNKS` |
| 单个区块结构 | `!c \|\| typeof c !== 'object' \|\| !Array.isArray(c.tiles)` |
| 区块坐标范围 | `cx/cy` 经 `int(..., -MAX_CHUNK_COORD, MAX_CHUNK_COORD)` 后须为有限数 |
| 最终非空 | `G.chunks.size === 0` |

**安全设计原则**：**任一校验失败即整体拒绝**（返回 `false`），不做部分加载 ——
部分加载会产生"半损坏的世界"，比明确失败更难排查。

> 【已实现】`saves.js sanitizeMeta()` 对存档元信息做白名单消毒。
> 安全测试 `test/browser/security-test.mjs` 用恶意存档验证
> **不会触发脚本、不会注入 DOM 节点**（5 条断言）。

## 四、写入路径（三条自动 + 一条手动）

### 4.1 三条自动路径

【已实现】决策逻辑在 `js/savepolicy.js`（纯逻辑），接线在 `main.js`

| 路径 | 触发 | 方式 | 节流 | 互斥判据 |
|---|---|---|---|---|
| **周期自动存档** | 每 `AUTOSAVE_SEC = 180` 游戏秒 | **异步分块** | 到点即写 | `isSaveBusy()` |
| **离场保存** | `beforeunload` **与** `pagehide` | **同步**全量 | `EXIT_SAVE_MIN_MS = 15000` 毫秒 | **不查忙**（靠槽位序号兜底） |
| **转后台保存** | `visibilitychange` → `hidden` | **异步分块** | 无 | `isSaveBusy()` |

### 4.2 为什么离场用同步、后台用异步

【出处：`main.js` 注释】

| 场景 | 约束 | 选择 |
|---|---|---|
| `beforeunload` | **无法 `await`**（页面即将卸载） | 必须同步写 |
| `pagehide` | 同上；移动端（尤其 iOS Safari）在"切到后台被系统回收"与 bfcache 往返时**不保证触发 `beforeunload`**，只触发 `pagehide`，此前会**静默丢档** | 必须同步写 |
| `visibilitychange` | 页面转后台后**通常仍存活足够时间** | 可异步分块，不阻塞渲染线程 |

**同步写的代价**：大图数 MB，同步 `stringify + setItem` 可达**秒级**。
故加 `EXIT_SAVE_MIN_MS = 15s` 节流：距上次成功写档 < 15 秒则跳过。
`beforeunload` 与 `pagehide` 相邻触发时，第二次会命中节流直接跳过，**不会重复全量序列化**。

### 4.3 ⚠️ 互斥判据的统一（2026-10 修复）

**修复前的问题**：三条路径各自检查不同的标志组合：

| 路径 | 原检查 | 漏项 |
|---|---|---|
| `tryAutosave` | `_autosaveBusy \|\| _saving` | 漏 `_bgSaveBusy` |
| `visibilitychange` | `_saving \|\| _bgSaveBusy` | **漏 `_autosaveBusy`** ← 缺陷 |
| 离场写 | 不查（靠序号） | —（刻意） |

**后果**：自动存档在飞时切后台 → **并发两份全量序列化**（同槽位，靠 `_slotSeq` 兜底正确性，
但 CPU / 内存翻倍）。

**修法**：统一为单一判据

```js
export function isSaveBusy(s){ return !!(s && (s.autosaveBusy || s.saving || s.bgSaveBusy)); }
```

**回归测试**：`test/rev-5-save-policy.test.mjs`（38 条断言）含双向验证
（自动存档在飞时不得发起后台写；后台写在飞时不得发起周期写）。

### 4.4 周期存档的累加器语义（易错点）

【已实现】`js/savepolicy.js autosaveTick()`

```js
const next = (acc || 0) + (dt || 0);
if(busy)      return { due:false, acc:next, reason:'busy' };   // ← 保留累加
if(next < intervalSec) return { due:false, acc:next, reason:'not-due' };
return { due:true, acc:0, reason:'due' };
```

**⚠️ 因"忙"而跳过时不得清零累加器** —— 否则这次到点被白白吞掉，
要再等**完整一个周期**（180 游戏秒）才会重试。
正确行为：忙解除后**下一帧立即触发**。

### 4.5 手动存档

【已实现】存档对话框（`ui.js`）支持：

|---|---|
| 写入指定槽 | 1 / 2 / 3 |

## 五、异步分块序列化（性能关键）

### 5.1 问题

大图存档的序列化 + `JSON.stringify` + `setItem` 是**长同步任务**，
若在 tick 内执行会把帧率打穿（实测本项目在软件渲染下 2–12 FPS，
一次同步存档可造成明显卡顿）。

### 5.2 修法

【已实现】`js/state.js serializeStateAsync()`

```js
const BATCH = 8;
for(let i = 0; i < list.length; i++){
  chunks.push(encodeChunk(list[i]));
  if((i + 1) % BATCH === 0){                    // 每 8 个区块
    onProgress?.({ pct: Math.round((i+1)/total * 40), stage:'serialize' });
    await yieldTo();                             // ← 让出主线程
  }
}
onProgress?.({ pct: 42, stage:'logs' });
await yieldTo();
```

| 机制 | 说明 |
|---|---|
| 批次大小 | 每 **8 个区块**让出一次主线程 |
| 进度回调 | `onProgress({pct, stage})`，用于 UI 进度条 |
| 让出方式 | `yieldFun`（默认 `setTimeout(r, 0)`） |
| 进度分段 | 序列化占 0–40%，日志 42%，后续由 `saves.js` 继续 |

### 5.3 槽位序号（"最新者获胜"）

【已实现】`js/saves.js`

**问题**：异步写在飞时，玩家可能又触发了另一次写（或离场同步写）。

**解法**：每次写入都 **bump 槽位序号**；在飞的旧异步写提交前校验序号，
若已被更新的写超越则**自动放弃提交**。

**为何不用复杂互斥**：
- 离场同步写必须能"抢占"在飞的异步写（否则真卸载时会丢档）
- 序号方案天然实现"最新者获胜"，无需等待或取消机制

> **这就是离场写刻意不查忙标志的原因** —— 靠序号兜底比互斥更安全。

### 5.4 配额处理

【已实现】`js/saves.js`

| 情形 | 处理 |
|---|---|
| 写入成功 | 返回元信息对象 |
| 写入失败（配额满/序列化失败） | **返回 `null`**（不抛错） |
| 调用方责任 | **必须检查返回值** —— 静默失败会让玩家以为一直在自动存档 |
| 首次失败 | 尝试**配额回收**（清理旧数据后重试） |
| 仍失败 | **裁剪日志**（`logCap` 降级）后重试 |

**自动存档的失败提示**【已实现】：

```js
.then(meta=>{
  if(meta){ _lastSaveOk = Date.now(); return; }
  console.warn('[autosave] quick FAILED (quota / serialize)');
  if(!_autosaveWarned){ _autosaveWarned = true; toast('自动存档失败，请手动保存或导出存档'); }
})
```

**去抖**：`_autosaveWarned` 保证只提示一次（避免反复打扰）。

## 六、账号系统（本地）

### 6.1 数据模型

【已实现】`js/auth.js`，`td/users`

```
{
  <username>: {
    salt: <hex>,
    hash: <hex>,
    kdf: 'PBKDF2-SHA256' | 'FNV-1a-weak',     ← 关键：如实记录算法
    createdAt: <timestamp>
  }
}
```

### 6.2 双路 KDF

| 上下文 | 算法 | 安全性 | 标注 |
|---|---|---|---|
| **安全上下文**（HTTPS / localhost） | **PBKDF2-SHA256**（Web Crypto `crypto.subtle`） | 强 | `kdf: 'PBKDF2-SHA256'` |
| **非安全上下文**（纯 HTTP 域名） | **FNV-1a**（降级） | 弱 | `kdf: 'FNV-1a-weak'` + console 告警 |

**设计原则（重要）**：

> 降级时**如实标注 `kdf: 'FNV-1a-weak'`**、在 console 明确告警，
> **绝不冒充强哈希**。读取时按记录的 `kdf` 标签走对应验证路径，故旧档可正常登录。

**安全测试断言**【已实现】`test/browser/security-test.mjs`：

| 断言 | 含义 |
|---|---|
| `kdfSpoofed = false` | 降级算法**未冒充**强哈希 |
| `weakHashHonestlyLabeled = true` | 弱哈希被如实标注 |

### 6.3 与 HTTPS 的关系（部署必读）

$$crypto.subtle \text{ 可用} \iff \text{安全上下文（HTTPS 或 localhost）}$$

**故 HTTPS 不是可选项，而是安全前提**。
纯 HTTP 部署会让所有密码走弱哈希 —— 虽然本项目是本地账号（密码不外传），
但同一密码可能被玩家复用于其他站点，弱哈希会降低其被破解的成本。

> 详见 `13_构建部署与发布.md §HTTPS`。

## 七、事件日志

【已实现】`js/log.js`

### 7.1 压缩编码

日志以 **`[code, t, x, y]` 四元组**存储，而非可读字符串：

| 字段 | 含义 |

**类型码样例**

| code | 事件 |

| 11 | 神迹·加速建造 |
| 12 | 神迹·天降甘霖 |
| 30 | 时代进阶 |

### 7.2 上限与裁剪

| 项 | 说明 |
|---|---|
| 上限 | `SAVE_LOG_CAP`（保留最近 N 条） |
| 裁剪时机 | 序列化时（`logSliceOf`），超出取**最后** N 条 |
