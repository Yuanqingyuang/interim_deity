## 一、世界模型

### 1.1 三层坐标

| 层 | 单位 | 说明 |
|---|---|---|
| **世界坐标** | 地块整数索引 $(x, y)$ | 无限延伸，可为负 |
| **区块坐标** | $\lfloor x / CHUNK \rfloor,\ \lfloor y / CHUNK \rfloor$ | `CHUNK = 10`，即每块 10×10 = 100 格 |
| **世界单位** | $x \times TILE$ | `TILE = 1.0`，Three.js 场景坐标 |

【已实现】区块键为字符串 `` `${cx},${cy}` ``（`state.js chunkKey()`）。

### 1.2 地块数据结构

【已实现】每格由 `makeTile()` 创建，字段如下（`state.js`）：

| 字段 | 类型 | 含义 | 默认 |
|---|---|---|---|
| `h` | number | 地表高度（世界单位） | 由地形采样 |
| `water` | 0/1 | 是否水面（`h ≤ WATER_LEVEL`） | — |
| `tree` | 0/1 | 是否有树 | 0 |
| `zone` | 0–4 | 分区：0 空 / 1 居住 / 2 农田 / 3 工业 / 4 信仰 | 0 |
| `prog` | 0–1 | 建造进度 | 0 |
| `built` | bool | 是否已建成 | false |
| `variant` | 0–2 | 外观变体（由哈希决定，确定性） | `(hash2(x,y,seed+13)×3)\|0` |
| `live` | bool | 是否已初始化（**全仓无读取方**，见 `15` 文档死代码清单） | true |

**渲染期临时字段**（不入存档）：`_wx` / `_wy` / `_wz` 由 `render.syncWorld()` 写入。
【已实现】`state.js encTile()` 显式列举 7 个字段，故这些临时字段**不会**污染存档。

### 1.3 关键常量

| 常量 | 值 | 位置 | 含义 |
|---|---|---|---|
| `TILE` | 1.0 | `config.js:7` | 地块边长（世界单位） |
| `CHUNK` | 10 | `config.js:20` | 区块边长（格） |
| `START_CHUNKS` | 4 | `config.js:21` | 开局生成 4×4 区块（以原点为中心） |
| `WILD` | 18 | `config.js:23` | 城区外延伸的旷野格数（地形网格覆盖范围） |
| `MAXH` | 9 | `config.js:8` | 地形高度上限 |
| `MINH` | 0.2 | `config.js:9` | 地形高度下限 |
| `WATER_LEVEL` | 0.75 | `config.js:10` | 水陆判据线 |

## 二、地形生成

### 2.1 生成管线

```
continentField(大陆场)  ──→ 决定海陆（径向衰减）
        │
        ├─ 海洋分支: h = mix(MINH, WATER_LEVEL − 0.06, t)
        │
        └─ 陆地分支: landElevation(ridged + fbm 噪声) → h
                          │
                          ├─ 出生地羽化平整（半径 3.2–5.0 格）
                          │
                          └─ 河谷高程包络 × 河道冲刷  ← sampleHeight
```

### 2.2 海陆判据与"岛屿硬上限"

【已实现】`terrain.js heightAt()` 用 `continentField` 的径向项 `smstep(0.55, 1.05, dw)`，
其中 $d_w = \sqrt{x^2+y^2} / 90$。

**实测结论**【已实现·实测】：**半径 ≥ 94 格处恒为海洋**。
故岛屿可建造格实测仅 **4,979 ~ 5,881 / 种子**。

> **这条硬上限是全项目最重要的约束**，它直接导致了：
> ① 建筑代理比 `BUILD_Q`（1 格 = N 栋）
> ② E5 人口目标从 10 万下调到 6 万
> ③ 自动建造的放置目标使用**地块口径**而非逻辑口径
> 详见 `09_数值与公式手册.md §9`。

### 2.3 河道【已实现·2026-10 修复】

**修复前的问题**【已实现·已修复】：河道掩码是**纯噪声**、无高程约束，
实测河道占陆地 34–47.5%，其中 **75–77% 落在山地**（占比随高程**单调升高**：
0.75–1.2 带 10.4% → 6+ 带 **80.0%**），即**河流几乎只长在山顶**，与真实地貌相反。
且冲刷公式最多只把高度降到 $0.8h$，导致 **57–67% 的"河道"是干沟**（河床高于水面）。

**修复方案**：

$$E_{river}(h) = \underbrace{\text{smstep}(W_L+0.10,\ W_L+0.55,\ h)}_{\text{水线附近渐入}} \times \underbrace{\Big(1 - \text{smstep}(2.6,\ 4.6,\ h)\Big)}_{\text{高地归零}}$$

其中 $W_L = 0.75$ 为水面高度。河道掩码乘以此包络后，再用阈值 $RIVER\_THRESHOLD = 0.50$ 判定。

**修复后实测**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 河道占陆地 | 34–47.5% | **11.1–17.2%** |
| 高山河道（$h>4.6$） | 33–43% | **0%** |
| 干沟率 | 57–67% | **16–18%** |
| 内陆水面（真河） | 32–43% | **82.5–83.7%** |

> **顺带建立的单一来源常量**：
> - `terrain.js WATER_PLANE_Y = WATER_LEVEL − 0.04` —— 水面网格的实际高度
> - `terrain.js RIVER_THRESHOLD = 0.50` —— 河道判据阈值
>
> 原先 `0.28` 硬编码在冲刷逻辑内，与掩码幅度耦合却无显式关系，调一处忘另一处即静默失效。

### 2.4 水格不变量【已实现·2026-10 新增】

**问题**：水陆判据是 $h \le 0.75$，而水面网格画在 $0.71$（低 0.04 以避开岸边 z-fighting）。
故 $h \in (0.71,\ 0.75]$ 的格**被判为水、却高出水面** —— 实测每区块 20–25 格。

**修法**：在 `fillTileFromNoise()` 内建立**不变量** —— 凡 `water = 1` 的格，
其高度必须低于 `WATER_PLANE_Y`。判据值本身不变，故"能否建造"的口径也不变。

**修复后实测**：高于水面的水格 **21/25/20 → 0/0/0**。

### 2.5 确定性保证【已实现】

> 规格要求：**同种子必须产出同一世界**。

实测保证手段：
- `genWorld()` 期间 `Math.random` 调用数 **= 0**（替换计数法验证）
- 同种子两次生成 1,600 格**逐位相同**（3 种子验证）
- 所有随机性来自 `hash2()` / `mulberry32()` / 值噪声 / fbm

> ⚠️ **但有一处例外**【推断，据代码】：`autoRng(G, salt)` 以
> `mulberry32(seed + ⌊G.time × 2⌋ × 9973 + salt)` 为源，而 `G.time` 由 `dt` 累加。
> 因此**地形可复现，但城市演化不可复现**（不同帧率下自动建造的采样序列不同）。
> `15_问题术语与TODO.md` 已登记。

## 三、放置规则（核心）

### 3.1 两套规则：手动 vs 自动

| 规则集 | 函数 | 用途 | 严格度 |
|---|---|---|---|
| **手动放置** | `terrain.js canPlaceZoneManual()` | 玩家点击/拖拽 | **宽松**（不强制间隔与工业距离） |
| **自动放置** | `terrain.js canPlaceZoneAt()` | 子民自动建造 | **严格**（含间隔与工业距离） |

> **这是一处刻意的设计**：玩家可以自由规划（否则手动划地会处处被拒、体验极差），
> 而子民必须守规矩（否则城市会长成不可读的一团）。

### 3.2 通用前置条件（两套共用）

【已实现】`terrain.js canPlaceZoneManual()`

| 条件 | 判据 | 说明 |
|---|---|---|
| 地块存在 | `getTile(G,x,y) !== null` | 越界返回 null |
| 非水面 | `!t.water` | |
| 未占用 | `t.zone === 0` | 已划区不可覆盖 |
| **高度区间** | $0.95 \le h \le 5.4$ | 过低的滩涂与过高的岩雪不可建 |

> **高度区间是玩家的主要限制**。沙滩段（$h \lesssim 0.95$）与岩石/雪段（$h \gtrsim 5.4$）
> 都不可建造，玩家需要用神力「抬升」或「平整」把地形改到可建区间。

### 3.3 农田的额外规则【已实现】

`terrain.js canPlaceZoneAt()` 中，`zoneType === 2`（农田）时检查：

$$\text{neighRes} = \#\{\text{8 邻域中的居住格}\}, \quad \text{orthRes} = \#\{\text{4 正交邻域中的居住格}\}$$

要求：

$$\text{neighRes} < 5 \quad \wedge \quad \text{orthRes} < 3$$

**设计意图**：农田可以贴近居住区（供养关系合理），但**不能被居住区包围**（否则无法扩张）。

### 3.4 工业的硬约束【已实现】

`zoneType === 3`（工业）时，在 $[-6, 6]^2$ 邻域内搜索最近的居住格，计算**切比雪夫距离**：

$$D_{res}(x,y) = \min\Big\{\max(|dx|, |dy|) \;\Big|\; \text{格}(x+dx,\ y+dy)\ \text{为居住区}\Big\}$$

要求 $D_{res} \ge R_{ind} = 6$（`formulas.js:53 LAYOUT.R_ind`）。

**设计意图**：工业区必须离居民区足够远（污染/分区感），这使城市呈现"居住中心 + 工业外环"的布局。

### 3.5 间隔规则（8 邻域空置）【已实现】

`terrain.js zoneNeedsGap(zoneType)` 返回 `zoneType !== 2`，即：

> **仅「农田-农田」可以相邻；其余任意组合至少空 1 格。**

具体判定：遍历 8 邻域，若存在已划区格 $a$，则
- 当 `zoneType === 2 && a.zone === 2` 时**允许**（农田连片）
- 其余情况**拒绝**（必须间隔）

**这条规则的深远影响**：

$$\text{非农田建筑密度} \le 25\%$$

因为每栋建筑至少要占「自身 + 8 邻域空」中的一部分，在最优排列下密度上限约 1/4。
结合 §2.2 的岛屿硬上限，得到：

$$\text{建筑地块硬上限} \approx 4{,}979 \times 0.25 \approx 1{,}245 \sim 1{,}350$$

> 【已实现】用户已明确确认此规则为**有意设计**，不得更改。
> 故所有"地图装不下"的问题都通过**代理比**解决，而非放宽间距。

### 3.6 规则速查表

| 条件 | 手动 | 自动 | 代码 |
|---|---|---|---|
| 非水 / 未占用 | ✔ | ✔ | 两者 |
| $0.95 \le h \le 5.4$ | ✔ | ✔ | 两者 |
| 农田邻接居住上限 | — | ✔ | `canPlaceZoneAt` |
| 工业 $D_{res} \ge 6$ | — | ✔ | `canPlaceZoneAt` |
| 8 邻域空置 | — | ✔ | `canPlaceZoneAt` |

## 四、自动选址：打分场

### 4.1 流程

【已实现】`terrain.js findAutoSite(G, zoneType)`

```
1. 采集全部居住格坐标（tileIndex 缓存）→ 计算居住质心 (cx, cy)
2. 以质心为中心，按半径档位向外扫描候选格（固定 96 次采样）
3. 对每个合法候选格调用 scoreIndustrialCell / 对应打分函数
4. 取分数最高者返回 [x, y]；全不合格返回 null
```

### 4.2 打分权重【已实现】

`formulas.js:63 LAYOUT` 定义五项权重：

| 权重 | 值 | 含义（据代码推断） |
|---|---|---|
| `w1` | 3.0 | 到居住区距离（越近越好，但受硬约束） |
| `w2` | 2.0 | 邻接同类数量（聚集倾向） |
| `w3` | 1.5 | 地形平整度 |
| `w4` | 2.5 | 与异类簇的距离 |
| `w5` | 2.0 | 到质心的距离（紧凑倾向） |

> 【待确认】权重的精确语义需读 `scoreIndustrialCell()` 全文确认；
> 上述为据 `formulas.js:63` 注释与调用点的**推断**。

### 4.3 布局参数

`formulas.js:52 LAYOUT`：

| 参数 | 值 | 含义 |
|---|---|---|
| `R_ind` | 6 | 工业距居住最小切比雪夫距离 |
| `D_max` | 8 | 异类簇最大中心距 |
| `BlockCap` | 25 | 单区块建筑容量 |
| `w1`…`w5` | 3.0/2.0/1.5/2.5/2.0 | 打分权重 |

> 【已实现·已清理】原 `LAYOUT.batch`、`LAYOUT.CHUNK`、`LAYOUT.R_farm`、
> `LAYOUT.D_chunk_max`、`LAYOUT.gap_min`、`LAYOUT.gap_farm` 均为**全库零引用死值**，
> 已于 2026-10 删除。其中 `CHUNK` 曾被 `terrain.js` 与 `state.js` 分别从
> `LAYOUT` 与 `config` 取值 —— 两处定义分裂在两条路径上，任一处改动都会造成
> 区块尺寸理解不一致的**静默错位**，故统一到 `config.js`。

## 六、世界扩张

### 6.1 触发

【已实现】放置地块时调用 `terrain.js ensureChunkRing(G, wx, wy)`，
以目标格为中心**预生成 3×3 区块**，保证 `getTile` 能命中（避免"在未生成区域放东西"）。

### 6.2 地形网格重建

【已实现】`render.js buildTerrain(G)`

| 项 | 实现 |
|---|---|
| 网格数 | **全世界一张** `BufferGeometry`（非每区块一张）→ **区块间不存在裂缝** |
| 顶点索引 | $(gx, gy)$，世界坐标 $((ox+gx)\cdot TILE - TILE/2,\ h,\ (oy+gy)\cdot TILE - TILE/2)$ |
| 覆盖范围 | $GW = (\text{城区宽}) + 2 \times WILD$，$W = GW + 1$ |
| 格中心高度 | 四角均值 $= \frac{1}{16}[1,2,1] \otimes [1,2,1]$ 作用核（**见 §6.3**） |
| 颜色 | 顶点色，五段连续（沙滩→草→深草→岩→雪） |
| 节流 | `terrainDirty` 标记 + 0.1s / 0.15s 间隔 |
| 索引复用 | `Uint32Array` 按 `W/H` 缓存，尺寸不变时零分配（原实现每次重建 ~2MB） |
| 版本号 | 每次重建递增 `_terrainVer`，使拾取缓存失效 |

### 6.3 格中心高度（建筑贴地基准）

【已实现·2026-10 修复】

网格的角点 $(gx, gy)$ 高度为**其周围 2×2 格高度的均值**：

$$H_{corner}(gx, gy) = \frac{1}{4}\sum_{dx \in \{-1,0\}}\sum_{dy \in \{-1,0\}} h\Big(ox+gx-1+dx,\ oy+gy-1+dy\Big)$$

格 $(x,y)$ 的 quad 由角 $(x-ox,\ y-oy)$ 起的四个角组成，故格中心高度为**四角均值**：

$$H_{center}(x,y) = \frac{1}{4}\Big(H_{corner}(g_x, g_y) + H_{corner}(g_x\!+\!1, g_y) + H_{corner}(g_x, g_y\!+\!1) + H_{corner}(g_x\!+\!1, g_y\!+\!1)\Big)$$

其中 $g_x = x - ox,\ g_y = y - oy$。

**修复前的问题**【已实现·已修复】：
`render._surfaceY()`（建筑贴地所用）原先是"自格 + 四正交邻"的 **5 点十字均值**，
与网格的四角核**不一致**。实测偏差：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 平均 $|\Delta|$ | 0.057–0.068 | **0.000** |
| 最大 $|\Delta|$ | 0.853 | **0.000** |
| $|\Delta| > 0.05$ 占比 | 39–42% | **0%** |
| 浮空 / 埋地格数 | 约 300 / 300 | **0 / 0** |

> 建筑总高仅 0.9–2.2 世界单位，故 0.85 的贴地误差是**肉眼可见**的。
> 修复要点：`_surfaceY` 必须完全复刻网格的 `heightOf`（取 `t.h` **原值**、
> **不做** `MIN_H_SAFE` 钳制），并复用同一套 `ox/oy/W/H` 以命中旷野高度缓存。

### 6.4 旷野暗角【已实现·2026-10 修复】

托管格（已生成区块）与旷野格（网格覆盖但未生成）之间原先有**亮度跳变**：

- **修复前**：暗角按"到包围盒**中心**的距离 ÷ 半跨度"计算，而托管/旷野是按**格是否存在**判定
  → 两个判据边界不重合 → 托管最外格 `dim=1.0`、紧邻旷野格 `dim≈0.73`，
  **一格内亮度跳 27%**（大世界 35%）；且 `dim` 依赖包围盒尺寸，
  **每次世界扩张整圈旷野颜色都会变**
- **修复后**：改为"离托管区包围盒的**外接距离**"（切比雪夫），边界处为 0、向外按 0.02/格渐深、
  17.5 格后到最深 0.65 → 跨界一格跳变 **27% → 2%**
