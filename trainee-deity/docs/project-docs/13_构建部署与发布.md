## 一、总体特性：本项目**没有构建步骤**

| 常见构建环节 | 本项目状态 |
|---|---|
| 打包器（webpack/vite/rollup） | 【不适用】**无** |
| 转译（Babel/TS） | 【不适用】**无**，源码即产物 |
| 代码压缩 / 混淆 | 【不适用】**无** |
| 资源指纹（hash 文件名） | 【不适用】**无**（因此必须 `no-cache`，见 §五） |
| Tree-shaking | 【不适用】无 |
| 环境变量注入 | 【不适用】无（`APP_VERSION` 直接写在源码） |

**"发布"= 把一批白名单文件复制到静态站点根目录。**

$$部署 = \text{复制文件}$$

### 1.1 收益与代价

| | 内容 |
|---|---|
| **收益** | 部署零构建、调试时错误行号直指源文件、完全离线可玩、无 npm 运行时依赖 |
| **代价** | ① 无指纹 → 必须 `no-cache`；② 源码可读（无混淆）；③ 需要浏览器支持 ES Module + importmap（现代浏览器均可） |

### 3.3 ⚠️ 打包后必做的验证（两次真实教训）

| 教训 | 说明 |
|---|---|
| **包内容与源码不同步** | 新增模块（如 `savepolicy.js`、`autobuild.js`）后若忘记重打包，**部署后游戏直接跑不起来**（`main.js` 的 `import` 失败） |
| **"验证"可能打到了源码而非包** | 曾在 8899 起服务验证部署包，但该端口已被**更早的进程**占用（`pwsh-197` 报 `EADDRINUSE` 启动失败），实际提供内容的是旧进程 —— 差点误判 |

**故必须做"标记 + 字节级"双重确认**：

| 手段 | 做法 |
|---|---|
| **title 标记** | 在解压出的 `index.html` 里注入 `<title>PKG-{commit}</title>`，与源码端口对比确认无歧义 |
| **字节级比对** | 对包内文件与 HTTP 提供的字节做 SHA256 逐文件比对（`index.html` 因注入标记而预期不同） |

**推荐验证流程**：

```bash
# 1. 解压到临时目录
Expand-Archive dist/trainee-deity-v1.1.0.zip -DestinationPath /tmp/pkgtest

# 2. 注入标记（便于区分多个服务实例）
#    把 <title> 改为 PKG-<commit>

# 3. 起服务于独立端口（先确认端口空闲！）
node tools/serve.mjs <pkgdir> 8899

# 4. 确认打的是包
curl -s http://127.0.0.1:8899/ | grep '<title>'      # 应显示 PKG-<commit>
curl -s http://127.0.0.1:8080/ | grep '<title>'      # 源码端口应显示原 title

# 5. 对包跑浏览器回归
GAME_URL=http://127.0.0.1:8899/ node test/support/run-browser.mjs

# 6. 字节级比对（见上）

# 7. 停止测试服务并清理临时目录
```

### 3.4 校验和核对

```bash
# 独立重算并与 .sha256 文件比对
Get-FileHash dist/trainee-deity-v1.1.0.zip -Algorithm SHA256
```

**实测结果**：zip 与 tar.gz 的校验和均与 `.sha256` 文件匹配 ✔

## 四、部署方式

### 4.1 方式 A：宝塔面板（推荐给运维）

【出处】`docs/deploy.md`

| 步骤 | 操作 |
|---|---|
| 1 | **网站 → 添加站点**：填域名，PHP 选 **纯静态** |
| 2 | **文件**：进站点根目录，上传并解压；**根下必须直接是 `index.html`** |
| 3 | **网站设置 → 配置文件**：确认 `root`；`.js` 使用 `application/javascript` |
| 4 | **域名 DNS**：A 记录 → 服务器 IP |
| 5 | **SSL**：申请证书并**强制 HTTPS**（**必须**，见 §六） |

### 4.2 方式 B：任意静态托管

只需能正确返回文件即可（Nginx / Apache / Caddy / 对象存储 + CDN）。

**唯一硬性要求**：根目录下直接是 `index.html`（**不能多一层目录**）。
本项目打包时根下直接是 `index.html`，解压即用 ✔

### 4.3 方式 C：本地调试

```bash
python3 -m http.server 8080
# 或
npx serve .
# 或（本项目自带）
npm run serve          # node test/support/serve.mjs 8080
npm run serve:test     # :8765
```

**⚠️ 不能用 `file://` 打开** —— ES Module 与 `importmap` 在 `file://` 下受 CORS 限制。

### 4.4 Nginx 配置

【出处】`docs/deploy.md`

```nginx
server {
  listen 443 ssl http2;
  server_name game.example.com;
  root /www/wwwroot/game.example.com;
  index index.html;

  location / { try_files $uri $uri/ /index.html; }

  # ⚠️ 本项目无构建哈希 → 必须 no-cache，否则改版后老用户跑旧代码
  location ~* \.js$  { default_type application/javascript; add_header Cache-Control "no-cache"; }
  location ~* \.css$ { default_type text/css;              add_header Cache-Control "no-cache"; }
}
```

**补充建议**（本项目特性带来）：

```nginx
  # Three.js 是不可变版本号路径，可给长缓存（其内容永不改变）
  location ^~ /vendor/three@0.161.0/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
  }

  # SVG 与 markdown 同样建议 no-cache（无指纹）
  location ~* \.(svg|md)$ { add_header Cache-Control "no-cache"; }

  # 安全响应头（本项目未设置 __Host- cookie，故 CSP 相对简单）
  add_header X-Content-Type-Options "nosniff" always;
  add_header Referrer-Policy "same-origin" always;
```

> 【待确认】`index.html` 内是否已声明 CSP（`index.html` 247 行，
> 据 `02` 文档描述含 CSP）。部署时若 Nginx 再加一份需注意**不要冲突**。

### 4.5 缓存策略详解（本项目特有陷阱）

**问题**：本项目**无构建哈希** → 文件名不变（永远是 `js/main.js`）。

**若配置长缓存会发生什么**【已实现·实测踩过】：
改版后老用户仍跑**旧 `styles.css` 与 `saves.js`**，表现为
"界面样式没变"或"存档行为异常"，且**难以排查**（因为用户不会主动清缓存）。

| 路径 | 建议缓存策略 | 理由 |
|---|---|---|
| `js/*.js` | `no-cache` | 每次改动内容都变，但文件名不变 |
| `styles.css` | `no-cache` | 同上 |
| `index.html` | `no-cache` | 入口，必须最新 |
| `favicon.svg` | `no-cache` | 同上 |
| `vendor/three@0.161.0/*` | `max-age=31536000, immutable` | **路径含版本号**，内容永不改变 |

## 五、HTTPS（**必须，不是可选**）

### 5.1 原因：密码 KDF 依赖安全上下文

$$crypto.subtle \text{ 可用} \iff \text{安全上下文}$$

**安全上下文** = HTTPS，或 `localhost` / `127.0.0.1`。

### 5.2 非 HTTPS 的后果

| 上下文 | KDF 算法 | 安全性 | 标注 |
|---|---|---|---|
| HTTPS / localhost | **PBKDF2-SHA256** | 强 | `kdf: 'PBKDF2-SHA256'` |
| **纯 HTTP 域名** | **FNV-1a**（降级） | **弱** | `kdf: 'FNV-1a-weak'` + console 告警 |

**设计原则（重要）**：降级时**如实标注并告警，绝不冒充强哈希**。
安全测试有专门断言：`kdfSpoofed = false`、`weakHashHonestlyLabeled = true`。

### 5.3 为什么即使"本地账号"也必须上 HTTPS

| 论点 | 说明 |
|---|---|
| 密码可能被复用 | 玩家常用同一密码注册多个站点；弱哈希会降低其**在其他站点**的安全性 |
| 浏览器会标记"不安全" | 影响玩家信任与转化 |
| 传输层窃听 | 纯 HTTP 下所有资源与存档导入导出内容可被中间人读取 |
| 存档导入导出 | 涉及本地文件读写，安全上下文更稳妥 |

**结论**：**HTTPS 是上线前置条件**，不是"推荐项"。

### 5.4 部署清单

| 项 | 必须 |
|---|---|
| 有效证书（Let's Encrypt 或商用） | ✔ |
| HTTP → HTTPS 强制跳转 | ✔ |
| HSTS（可选但推荐） | 建议 |
| 证书自动续期 | ✔ |

## 六、CI 流水线

【已实现】`.github/workflows/ci.yml`

### 6.1 两个 Job

| Job | 名称 | 依赖 | 内容 |
|---|---|---|---|
| **core** | Lint + Unit Tests | 无（零依赖） | `lint.mjs` + `run-all.mjs` |
| **browser** | Browser Regression | `needs: core` | Playwright Chromium + 7 个浏览器测试 |

**设计意图**：核心门禁**零依赖、必过**；浏览器回归独立 job，**不阻塞核心门禁**。

### 6.2 ⚠️ CI 的一处历史缺陷（已修复）

【已实现·已修复】注释中保留了完整记录：

> 静态服务必须从**游戏根目录**起（`index.html` 在 `trainee-deity/`），
> 从仓库根起会让 `/index.html` 返回 404；旧版用 `curl -sf ... && echo` 探测，
> **探测失败不影响 job 结论**，于是浏览器回归长期**静默跳过**。

**教训**：探测语句必须**能失败**（`exit 1`），否则"检查通过"是假象。
现 `test/support/serve.mjs` 自带「根下必须有 `index.html`」的前置校验，缺了直接失败。

### 6.3 本机运行 CI 等价命令

```bash
npm run verify            # = lint + 全部 Node 测试
npm run test:browser      # = 装依赖 + 跑 7 个浏览器测试
```

| 脚本 | 命令 | 说明 |
|---|---|---|
| `npm test` | `node test/support/run-all.mjs` | 17 个自动化测试 |
| `npm run lint` | `node test/support/lint.mjs` | 语法 + 危险模式检查 |
| `npm run verify` | lint && test | **提交前必跑** |

## 七、版本管理与发布流程

### 7.1 版本号位置

**单一来源**：`js/config.js:5`

```js
export const APP_VERSION = '1.1.0';
```

**取值处**：构建物文案、控制台 banner（`console.info(\`实习神明 v${APP_VERSION}\`)`）、
登录/主菜单的版本角标（`.ver-tag`）。

> **发版只改这一行**。

### 7.2 建议发布流程

```
1. 确认工作树干净、main 与 origin/main 同步
2. npm run verify                      （lint + 17 个 Node 测试）
3. npm run test:browser                （7 个浏览器测试，需静态服务）
4. 如涉及版本变更：改 config.js 的 APP_VERSION
5. node tools/package.mjs              （打包）
6. 解压到临时目录 + 注入 title 标记     （验证打的是包）
7. 对包跑浏览器回归                    （GAME_URL 指向包服务端口）
8. 字节级比对 + 核对 .sha256            （确认包内容）
9. 上传部署 → 强制 HTTPS → 打开页面确认
10. 确认 Cache-Control 生效（改一处可见文案，验证刷新后生效）
```

### 7.3 变更类型与风险

| 变更 | 风险 | 注意 |
|---|---|---|
| 新增 `js/` 模块 | **高** —— 忘记重打包会导致线上 `import` 失败 | 必须重打包 + 对包验证 |
| 改 `BUILD_Q` / `T(E)` | **高** —— 影响可达性与预算 | 跑 `r16` 测试 |
| 改存档结构 | **高** —— 破坏旧档兼容 | 加版本号 + 迁移路径 |
| 改配置常量 | 中 | 跑全量测试；回写规格文档 |
| 改 UI / 样式 | 低 | 确认 `no-cache` 生效 |
| 改文档 | 低 | — |

### 7.4 ⚠️ 回滚预案（**当前缺失，建议补充**）

【待确认】资料中**未见回滚流程**。建议补充：

| 项 | 建议 |
|---|---|
| 保留上一版部署包 | 每次发布后保留 `dist/` 历史版本 |
| 回滚步骤 | 用上一版包覆盖站点目录（本项目无构建，直接覆盖即可） |
| 存档兼容 | **回滚前确认新版存档结构是否与旧版兼容**（若已写入 v3 特性，回滚会导致读档失败） |

> 若新版引入了存档结构变更，回滚后旧代码可能读不了新存档。

## 八、开发环境故障处置（来自 v1 计划书，供存档）

> 【出处】`E:\sxsm\修改计划书.md` 附录 C —— v2 未覆盖，此处保留以免丢失。

### 8.1 症状

工作区 `E:\sxsm` **原先缺少当前用户的「写所有者」权限**，
导致**所有命令无法启动**（看似"命令失败"，实为文件系统 ACL 问题）。

### 8.2 处置

按 DSH 诊断脚本为 `E:\sxsm` 补上完全控制权限并验证通过。

### 8.3 回滚命令

```powershell
pwsh -NoProfile -File 'E:\sxsm\acl-backup-0d3f432c20774810b547d616d6774804.json.ps1' `
  -Path 'E:\sxsm' -AllowRoot 'E:\sxsm' `
  -Restore 'E:\sxsm\acl-backup-0d3f432c20774810b547d616d6774804.json'
```

**报告**：`E:\sxsm\acl-report-b6e6144fc9304b1d9e71fe8f23fd8152.jsonl`

### 8.4 另一类环境故障：Chromium IPC 被沙箱阻断

【已实现·已记录】在受限沙箱下运行 headless Chromium 时会报：

```
FATAL: mojo platform_channel.cc Check failed: 拒绝访问
```

**原因**：Chromium 的 mojo IPC 需要命名管道，而受限沙箱禁止进程打开命名管道。

**解法**：放宽文件策略后即可正常截图与跑测试（本项目浏览器测试需要此条件）。

> **同类现象**：Node.js 的 `child_process.spawn` 在 `stdio: 'pipe'` 下亦会
> `EPERM`（同为命名管道限制），而 `stdio: 'inherit'` / `'ignore'` 可正常。
> 这是**环境边界**，不是代码缺陷 —— 不要尝试"换一种写法绕过"。
